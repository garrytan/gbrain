# 后台任务与 PGLite 访问治理规划

日期：2026-10-03。状态：用户已批准底层执行架构，软件后台任务已实施，本地定向验收完成；提交后的 CI 与安装包验收由用户完成。

范围：原规划优先治理导入；用户后续明确批准将 GUI 导入、快速维护、深度整理统一改为软件任务。此次接入现有导入、同步、补向量和整理核心，普通流程不再启动 CLI 子进程或交接 PGLite。高级 CLI 保持原合同，在线 CLI 转交不在此次交付中。不扩展助手能力或另做样式改版。调查基于 PMBrain 1.4.15、HEAD 8f807804，实施统一产品版本为 1.4.16。参考 Cherry Studio 稳定发布 v2.1.4（072aab935a0340b3e5f288b8328f3aaae24c918d），以及 PGlite 官方文档。

## 1. 要解决的两个问题

1. 长流程应作为可观察、可取消、可恢复的后台任务运行，GUI、CLI 共用执行链路。切换页面不影响执行，重启后能查到真实结果。
2. 导入运行期间不能将扫描、解析、OCR、等待模型等所有时间都计为数据库独占。真正的 SQL 和写入事务仍须串行协调；PGLite 同一目录只能由一个运行时拥有。

需要区分三种范围：

| 范围 | 合理持续时间与影响 |
| --- | --- |
| 任务生命周期 | 可持续数分钟，不因此关闭搜索、助手、MCP |
| PGLite 实例所有权 | Sidecar 正常运行期间持有，不交给普通导入子进程；各调用方经服务访问同一实例 |
| SQL/事务与业务资源锁 | 数据库调用按引擎规则排队；写事务只覆盖必要提交，同一 Source 同一页面的修改需要一致性保护 |

保持单一所有者，不代表只能有一个用户功能。也不能让两个进程在“暂时没有 SQL”时同时打开同一目录。

## 3. Cherry Studio 的参考范围

以稳定标签 v2.1.4 为准，不以 issue 中的提案或 main 新代码作为已发布能力：

- [任务架构](https://github.com/CherryHQ/cherry-studio/blob/v2.1.4/docs/references/job-and-scheduler/overview.md)：JobManager 管理持久化状态与执行，SchedulerService 管理何时触发；领取任务的事务完成后，再在调度锁外执行 handler。
- [知识索引任务](https://github.com/CherryHQ/cherry-studio/blob/v2.1.4/src/main/features/knowledge/tasks/indexDocumentsJobHandler.ts)：读取、分块、生成向量与最终 writing 分阶段；慢阶段在知识索引修改锁外，最终材料写入受资源锁保护。
- [准备目录任务](https://github.com/CherryHQ/cherry-studio/blob/v2.1.4/src/main/features/knowledge/tasks/prepareRootJobHandler.ts)：扫描展开后才安排子项索引；知识库资源锁有自己的边界，不能概括为所有扫描都完全无锁。
- [数据库服务](https://github.com/CherryHQ/cherry-studio/blob/v2.1.4/src/main/data/db/DbService.ts)：业务数据库使用持久连接的 better-sqlite3/SQLite，配置 WAL，写事务为同步短事务。它不使用 PMBrain 的 PGLite 所有权交接方式。
- Cherry 的知识处理任务使用 recovery=abandon，退出后不默认重新花费 embedding 费用；任务持久化并不等于所有失败/重启都自动重跑。

借鉴任务持久化、阶段、资源锁和恢复策略；保留 PMBrain 的 BrainEngine、Source 隔离、模型预算与现有 PGLite/Postgres 数据合同。不迁移到 SQLite，不照搬队列并发值或复制其知识库删除/重建逻辑。

[PGlite 官方多客户端示例](https://pglite.dev/docs/multi-tab-worker)也是多个调用方代理到一个实例。其浏览器 Worker 实现不能直接替代 Bun/Sidecar，但单实例、多调用方的边界适用。

## 4. 建议架构

```text
Desktop / Admin / CLI
        │  提交任务、查询、取消；沿用认证与 Source 权限
        ▼
Sidecar：任务调度 + 现有核心业务 + 唯一 PGLite 实例
        ├─ minion_jobs：新任务状态唯一持久化来源
        ├─ 扫描/文档解析 worker：不创建 BrainEngine，不打开 PGLite
        ├─ OCR/向量请求：异步执行，无数据库长事务
        └─ 必要读取/提交：共用 owner engine，短事务，小批次

搜索 / 助手 / MCP ── 同一 Sidecar engine
```

新任务应走结构化 handler，不传任意 shell 字符串。CPU 较重或同步文件处理放到纯处理 worker；只改成 async 函数或放进后台队列，不会自动消除 JS 主线程阻塞。

PGLite 使用 owner 进程内调度，借用现有 MinionQueue/MinionWorker 的 inline 能力；外部解析 worker 不访问业务数据库。Postgres 继续保留现有独立 worker 能力。必须先做同 owner 内调度与现有租约/取消机制的定向验证，不能把 inline 复用写成已经完成的常驻调度。

任务状态写入本来就会调用数据库，但只是必要的小操作，不应因此把整个后台任务标成数据库独占。首版依赖现有引擎事务序列化，不额外引入一套包住整个业务函数的全局锁。持续写入应在批次间让出执行机会；已经执行的 SQL/事务不能被强行抢占。

## 5. 导入的完整链路

1. **提交**：校验资料路径、权限、Source、选项；短事务保存任务，返回任务 ID。相同输入的重复提交用现有幂等机制合并。
2. **扫描**：在纯文件处理 worker 收集清单，记录数量和跳过项；Source 解析、配置和去重查询经 owner 做必要短读。
3. **解析/OCR/分块**：复用现有解析及 OCR/分块能力；昂贵处理移出 owner 的同步主线程。不持有数据库事务。
4. **生成向量**：复用 Gateway、预算与限流；外部请求等待时搜索/MCP 正常处理。保留现有“embedding 成功后再原子提交页面”的合同，不悄悄改为无向量成功。
5. **提交**：按文件/有界批次，经 owner 调用已有写入核心。校验 Source、输入指纹和目标页面是否已变；同一 Source 同一页面的修改必须协调，防止解析期间发生删除或编辑后写回旧内容。在与业务提交相同的原子边界内，验证任务未取消且结果属于当前有效执行尝试，拦截旧租约/旧 worker 的迟到结果；具体如何复用现有队列与事务合同在阶段 A 验证。
6. **记录结果**：真实完成数、跳过数、失败文件、阶段、耗时、错误及检查点持久化；任务中心与导入面板读取同一记录。

处理产物保存在应用任务临时目录，仅任务清单/引用进入 job.data，避免把大文档正文或密钥塞进队列。源文件发生变化时重新校验，不复用旧解析结果。模型/向量维度发生变化时，在提交前检查运行指纹，禁止混入旧空间的向量。

完成标准仍是当前业务承诺：页面、分块及要求的向量已提交；不把“已提交后台任务”显示为“已导入完成”。大文档原有部分完成语义和检查点需要继续保留。

## 6. CLI 与任务中心的兼容

- Desktop/Admin 导入提交后即可离开面板，任务由 Sidecar 管理，不靠页面是否挂载。
- 现有 `pmbrain import` 保留等待结果、输出格式和非零退出码。原规划中的在线转交及新后台参数此次未实施；高级 CLI 仍受原有单 owner 保护。GUI 通过结构化任务 API 执行共同业务，不拼接 CLI 参数。
- 未运行 Desktop/服务时，前台 CLI 自己作为唯一 owner 使用同一执行能力；若需脱离终端的后台执行，则由受管理本地服务承担，不能让第二个 jobs work 进程抢库。无服务环境不能宣称已有后台执行能力。
- owner 已在运行但不可达时，返回真实错误；不自动杀 owner、不删除锁、不另开数据库、不假装切换为另一种导入方式。
- 复用现有 CLI/MCP 客户端和本地认证机制，但必须先确认目标服务对应同一个数据库/brain/Source。不能只猜一个 localhost 端口，也不能允许只读 MCP 凭证提交写任务或任意本地路径。
- 任务中心继续复用现有页面/API。新任务状态以 job 记录为准；旧 ConsoleRun 的 ID、轮询与取消接口在兼容期继续工作，正常排空正在执行的旧任务，不强行迁移其运行进程。
- 初期默认保守：解析并发有界，模型请求遵守提供商限流，写入提交串行。允许多个阶段任务等待外部响应，不代表并发打开多个 PGLite 实例。

## 7. 取消、重启与故障

- 取消先记录请求，停止新增处理和提交，向处理 worker/模型调用传递取消；正在提交的事务按引擎规则完成或回滚。取消确认必须等到实际执行停止，不能仅把任务行设为 cancelled 就允许另一个写任务接替。
- 借用 Minions 取消与租约机制时，需补“worker 停止确认”与业务检查点；现有 best-effort cancel 不能直接等同于整条导入安全取消。
- 页面关闭不取消任务；应用真正退出则遵守现有退出行为，记录中断/待恢复。重启恢复任务可见性，完成文件不重复导入；用户主动取消的任务不自动恢复。
- 纯扫描/本地解析等可安全恢复；可能重新花费模型费用的阶段默认等待用户继续，除非任务已有明确重试/预算授权。预算在整个任务及重试累计计算，不每次重置。
- 若模型已经返回成功、但结果尚未持久化就崩溃，记录为结果不确定，不自动重发；用户选择继续前显示可能产生重复费用。持久化阶段结果与业务提交的检查点需区分，不能声称跨外部模型请求实现恰好一次执行。
- 取消或断网后已完成内容保留；不会为回滚整个目录删除用户资料、页面或 Wiki。不能承诺模型供应商中断后一定不收费。
- 出错必须显示阶段和文件；不更换为无关替代业务。任务状态和已提交结果要可追溯。

## 8. 什么仍需要独占

数据库迁移、数据库切换、冷备份恢复及向量列维度变更等，保留维护级独占。这些不应作为会暂停并等待自身的普通任务 handler；先由外层维护控制暂停调度、排空活动事务/worker，再复用现有维护控制器。排空超时应中止维护，不能假装空闲。

普通扫描、解析、等待 OCR/embedding、任务查询、模型名称/目录修改，均不因其所属任务尚未结束而触发全局数据库 busy。大型 SQL 本身的等待是合理数据库排队，要与“进程交接停库”分开报告。

| C：Office/图片/目录 | 纯处理 worker、现有解析/OCR、文件级检查点、模型指纹、失败重试与背压 | 大目录与慢 OCR 不阻塞服务主线程；恢复不重导已完成文件、不混向量、不自动重新花费已取消任务费用 |

优先从导入改执行层，界面只接真实任务状态，不再进行样式改版。不增加第三套任务管理、数据库类型或实验自动化。普通产品只接已有允许使用的流程，不重新启用成熟度台账里撤下的实验调度。

主要修改候选：`src/commands/natural-lang/executor.ts`、`src/commands/serve-http.ts`、`src/commands/pmbrain-admin-routes.ts`、`src/commands/jobs.ts`、`src/core/minions/`、`src/commands/import.ts`、`src/core/import-file.ts`、`src/core/document/`，以及任务中心/导入面板的状态适配。Core 只提取可复用阶段和任务接口，不重写 PGLite/检索/Dream 引擎。

首选复用现有任务表的 JSON 字段，不预先新增 Schema。若验证证明确实需要迁移，再单独提交兼容设计并同时测试两种引擎，不能为了队列直接删除或拆分历史表。

## 10. 验收脚本应覆盖的用户场景

测试只用隔离临时库与合成资料，同时覆盖 PGLite、Postgres；不使用真实知识库做压力或恢复实验。

1. 导入期间让测试 OCR/embedding 服务故意等待 20 秒，仍可连续查询已有知识、进行 MCP 搜索、读取任务详情；不返回全局 pglite_busy、不重启 Sidecar。另测大文件 CPU 解析，避免只测试异步等待。
2. 同时提交两个不同 Source 的导入，检索并行可用，两个结果不串 Source；同名 slug 的不同 Source 不互相覆盖。
3. 同一文件重复提交只产生一次有效处理；同页并发编辑/删除时，旧处理结果不回填覆盖新数据。
4. 开始导入后切页、关闭面板，再打开能看到同一任务；进程重启后能看到中断原因与已完成文件。覆盖模型返回成功后、结果持久化或业务提交前的崩溃窗口，不自动重复请求，清楚显示结果不确定与可能重复费用。
5. 在排队、解析、外部请求、提交边界分别取消，确认停止后没有迟到写入；模拟旧租约/旧执行尝试延迟返回，验证提交时拒绝。已完成文件保留，可明确重试失败文件。
6. 断网、错误凭证、模型移除/切换、源文件变化、磁盘写满分别失败，显示原生原因，不标成完成、不混入旧向量。
7. CLI 在服务在线、离线、owner 存在但服务不可达时，行为符合合同；原前台命令输出、脚本退出码与权限范围保持兼容。
8. 数据库维护时暂停调度并排空，超时不执行维护；恢复正常后队列继续，不能出现 handler 等待自己排空的死锁。
9. 为服务实例记录 PID/连接次数、外部等待时长、实际事务时长、提交批次大小、查询响应与失败次数。慢外部请求期间同实例所有权不变，实际事务不覆盖等待区间；性能门槛以隔离夹具基线设定，不保证任意硬件固定毫秒数。
10. 构建最新 Admin/Sidecar/Desktop、检查资源一致性，真实 Windows 路径与打包运行闭环；提交后的准确 SHA 通过相关 CI 后才算实施完成。

## 11. 授权与边界

这是底层执行架构调整。用户已在后续消息中明确“按照规划执行”，并要求 GUI 原生任务及 PGLite 单 owner、多调用方，已授权编码。未修改用户知识库、原始资料、Wiki 或已有向量。

已批准并实施的方向是：**正常任务不交接 PGLite 所有权；Sidecar 单 owner 内调度持久化任务；耗时处理 worker 无数据库；复用现有 Minions 与业务核心。** GUI 默认一个长任务，其他读取与助手请求可并行处理；数据库写入按事务排队。在线 CLI 的认证与库身份发现尚未实施，不作为已有能力宣传。

回退边界：按业务类型启用新执行器，新任务失败不自动退回旧业务流程；升级前排空旧活动任务。保留旧核心和接口适配以便版本回退评估，不删除任务表、原始资料、Wiki 或现有向量；回退前也需停接新任务并确认 worker 已停止。

## 12. 实施结果与验收差异

- `src/product/tasks/` 使用现有 minion_jobs，保存任务、进度和结果；Bun Worker 调用结构化业务核心，通过 RPC 使用 Sidecar 的 owner engine，不创建第二个数据库实例。没有 Schema 迁移。
- 普通导入、上传、同步、补向量、快速维护、深度整理及已有自动维护入口接入同一队列；现有任务中心显示完成数、失败文件、取消和显式重试。高级 doctor、数据库/索引维护及旧高级命令仍保留原执行方式。
