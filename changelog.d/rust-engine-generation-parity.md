**The generation ledger reads answer in the same order on every engine, and Postgres, PGLite and a Rust brain agree on the same stored history.**

### Fixed
- The generation ledger reads behind `gbrain repair generations`, managed publications and fence publishes now return their rows in one fixed order, with text sorted by bytes. Before, PGLite returned some of them in storage order, and Postgres sorted source ids and keys by the database's language rules (so `a-z` and `ab` swapped places between engines).
- The purge scrub on a Rust brain now finds a purged number in stored generation history as Postgres prints it (`1.0`, `1.50`), and treats a stored JSON `null` as a value, as Postgres does. Before, it read `1.0` as `1` and could miss or over-count rows.
- `gbrain repair generations --since` takes an instant with a time zone (for example `2026-10-01T00:00:00Z`) on every engine. A bare date, a time with no zone or a word like `yesterday` now refuses with one clear message everywhere, instead of being read in the session time zone on Postgres and refused only on a Rust brain. The CLI already sends an instant, so CLI use does not change.
- Every engine now refuses a managed activation id that is not a UUID before it writes it. Before, one such row made the list of left-behind pages fail for every caller on Postgres.
- A Rust brain now reads the before-state of facts for a fact rows generation, as Postgres and PGLite do. Before, that read sent raw SQL and stopped on a Rust brain. A fact id that is not a whole number now refuses with one clear message on every engine.
- Every engine now refuses a generation context, proposal or completeness whose JSON holds a number past the double range (for example `1e400`), with one clear message. Before, Postgres and PGLite stored it and read it back as `Infinity`, and a Rust brain refused it with a different error. gbrain itself never writes such a number.
- A Rust brain now restores a fact rows generation and runs the consolidate phase's restored check and tie holds, as Postgres and PGLite do. Before, those steps sent raw SQL and stopped on a Rust brain.
- A Rust brain now reads the before-state of the takes a takes write deletes or replaces (the take rows generation), as Postgres and PGLite do. Before, that read sent raw SQL and stopped on a Rust brain. Other steps of `gbrain extract takes` still send raw SQL.
- A Rust brain now reads, numbers and retires the facts that conversation extraction writes to a page (the extracted facts generation), as Postgres and PGLite do. Before, those steps sent raw SQL and stopped on a Rust brain. A source prefix that holds `%`, `_` or `\` now refuses with one clear message on every engine.

### Changed
- On Postgres, an empty `gbrain repair generations` preview (nothing to apply) taken before this upgrade, for several sources whose ids sort differently by language rules and by bytes, may refuse its apply as `preview_changed` after it. Preview again and use the new hash; the refusal says so.
- A Rust brain now reads the derived pages its generations check (the dream summary, `think` synthesis and drift report pages, a transcript's synthesis outputs, atoms and Life Chronicle events) as Postgres and PGLite do. Before, this read sent raw SQL and stopped on a Rust brain. Writing those pages still stops on a Rust brain: the trust and taint writes of a derived page and retiring one still send raw SQL.
- A Rust brain now reads what atom extraction checks before it writes: the size and hash of the origin page, and the evidence that an atom page was written before the generation ledger existed (its saved versions and its committed write requests). Before, these reads sent raw SQL and stopped on a Rust brain. Writing atom pages still stops on a Rust brain: the source-hash stamp, the trust write and retiring an atom page still send raw SQL.
