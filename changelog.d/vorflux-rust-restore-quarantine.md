**A Rust brain restore can now refuse to publish work that would run by surprise, and a restored brain gets a fresh brain id.**

### Added
- The Rust store has a restore safety check and a restore step for the backup commands to call. The check counts unfinished write requests, recovery records, live effects, purges the backup lacks and kinds of record it cannot classify, and refuses with a named reason. `gbrain backup restore` will report it as `restore_step_unsupported` once that command calls the restore step; it does not yet. The step turns archived automation off, detaches sources from the old machine's folders, and cancels unfinished jobs. It does not revoke anything yet: a backup that holds a live OAuth client, a local writer registration or an access token is refused by name (`archived_authority`, or `unclassified_state` for tokens), and the error says to re-issue tokens on the live brain and restore from an archive taken without them, or to wait for the follow-up that adds revocation. Most MCP users have OAuth clients, so they cannot restore a Rust brain until that follow-up lands.
- A restored Rust brain gets a new brain id, so it is never the same brain as the one it was copied from. The old and the new id are in the restore report. If the process stops between the two writes that record the id, the next open repairs the file from the record.
- A restore refuses, and changes nothing, when it runs inside an open transaction, when rebasing page origins would put two live pages on one file, or when its settings list leaves out a setting the store holds. Windows and UNC page origins are kept unchanged and counted in the report; rebasing them is not done yet.

Postgres and PGLite brains are unchanged and keep `pg_dump` and the PGLite backup. Nothing to do on upgrade.
