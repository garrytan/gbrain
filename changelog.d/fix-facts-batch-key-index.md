**A fact-extraction batch is looked up by its batch key through an index, so the lookup no longer reads the whole extract_facts journal (#9302).**

### Fixed
- Before managed fact extraction admits a batch, it looks up the requests already journaled under the batch's key (`storedBatch`). No index held that key, so each lookup read every `extract_facts` receipt of the principal and decompressed its intent, which is mostly fact embeddings, to test it. On a personal brain every capture lane writes as one principal, so the cost grew with the journal: the reporter measured a 14.5 s mean on a small Postgres brain, the most expensive statement in the database. Migration v317 adds `persistence_requests_facts_batch`, a partial index on `(source_id, COALESCE(intent->>'batchKey', outcome->>'batch_key'))` for `extract_facts` requests, built CONCURRENTLY on Postgres and inline on PGLite. `gbrain repair request-indexes` and doctor `persistence_request_indexes` cover it. The lookup now runs as a BitmapOr of this index and the request-id index, and the predecessor-part read of a split entity group uses it too. On an in-memory PGLite brain with 3,000 receipts of about 37 KB, a lookup went from 306 ms to 0.34 ms (median of 7 rounds).
- Tests: `test/facts-batch-key-index-9302.test.ts` checks on PGLite that the lookup reaches the request table only through the batch-key and request-id indexes, and still finds a batch's receipts, including a compacted one whose key is kept only in its outcome. The index-count assertions in the request-index tests and the catalog, doctor and migration goldens list the new index.
