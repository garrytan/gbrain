**Re-adopting a shared-skill pack, or importing a reviewed skill proposal, no longer deletes a skill's files, makes a private skill visible, or drops the tools and routing it was published with; adoption now refuses such a skill by name and changes nothing.**

### Fixed
- When the v0.53.0 shared-content migration re-adopted a pack after a reviewed inventory edit, it republished each skill from its `SKILL.md` alone. A skill's reference, asset or script files were deleted from the content checkout, a skill published with `private: true` became visible to readers, and requirements, a description or triggers set through `put_skill` were dropped. Adoption now refuses such a skill by name (`local_conflict`): it writes nothing and deletes nothing, and it names the skill and the `import_skill_proposal` remedy. New skills and prose-only skills adopt as before.
- `import_skill_proposal` refuses a proposal that would change a published skill's private flag, requirements, description or triggers, or widen a file's audience, and refuses while `skillpack.json` declares a skill that is not published yet (the import would drop it from the manifest).
- Adoption publishes only the bytes whose hashes you reviewed. A `SKILL.md` or `skillpack.json` changed after the review, or a `SKILL.md` that was not in the reviewed inventory, is refused.
- An adoption accepted by an older release and resumed after the upgrade gets the same check before it touches the checkout.
