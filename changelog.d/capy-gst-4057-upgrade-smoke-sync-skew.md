**`gbrain upgrade` no longer reports a healthy upgrade as broken when Bun's bin directory is not on PATH, and `gbrain sync` no longer fails with a cryptic missing-export error when a `gbrain serve` started before the upgrade is still running.**

### Fixed
- `gbrain upgrade` now checks the release it just installed by running that gbrain directly from Bun's bin directory (or the release binary itself) instead of looking `gbrain` up on PATH. From a shell without `~/.bun/bin` on PATH (a non-interactive bash, CI, Bun added only in `.zshrc`), a healthy upgrade used to fail its start check with `Executable not found in $PATH`, suggest a downgrade and leave a standing `upgrade_errors` warning in `gbrain doctor`. The version check, post-upgrade, the feature scan and the restart use the same path. A release that really does not start still fails and names the way back, and a gbrain that cannot be found at all is reported as not found, without the downgrade advice (#10536, reported by @yitzhakbg).
- `gbrain sync` on a Postgres brain no longer hands its run to a live `gbrain serve` whose recorded build is older than the CLI. Such a serve keeps the code it started with, and after an upgrade its next lazy import fails on a missing export. The sync now runs beside the serve and prints one line naming both versions and the restart (`gbrain upgrade --restart-only`). A delegated run that still fails this way inside a serve, on Postgres or PGLite, stops with `serve_build_skew`, which names the serve's pid and build, this CLI's version, the restart and, on Postgres, `GBRAIN_SYNC_NO_DELEGATE=1` to sync beside the serve meanwhile (#10537, reported by @yitzhakbg).
