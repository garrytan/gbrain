- `src/core/engine-sql/persistence-admission.ts` + `src/core/rust-engine/store-members/persistence-admission.ts` + `rust/crates/gbrain-store/src/persistence/worktree_admission.rs` — the managed-worktree admission reads as engine members: `readWorktreeAdmission` (the worktree row under a share lock, then its active refresh, locked when the refresh barrier is on, and whether the source binding holds; Postgres sends both statements before it waits), `completeSyncedRefresh` (completes a `syncing` refresh whose member sources reached its target head), `hasDeferralRoom` (no live consumer on the worktree's owner host lacks a capability), `readRefreshTiming` (a refresh's running time and the median of its worktree's last 10 completed refreshes) and `countHeldBehindImport` (the deferred writes not yet released that wait on a source's import or refresh). `persistence/journal.ts` admission and `persistence/refresh-retry-hint.ts` call them; each text is the statement they sent through `executeRaw`, written as static strings and pinned to the refresh schema constants by `test/persistence-admission-sql.test.ts`. The Rust store keeps refresh rows under `d 0x10` and the worktree and binding rows the writer claim stores under `d 0x09`, so admission reads `bound` from them (rust/docs/store/persistence.md). The members are classified `managed_persistence`, which the Rust engine holds back (`store-capabilities.ts` `HELD_FOR_CALLERS` names the bound-write sites that still run raw SQL: `compareFileTarget`, `guardOwnership`, publication recovery and `withTopologyLocks`), so a write to a bound worktree refuses `engine_capability_missing` at admission and writes no request row; an unbound write and an unbound grouped admission are served. Pinned by `test/engine-parity/persistence.test.ts`.

- `src/core/persistence/capability-retry.ts` — the retry limit of a write an engine refuses at publication with its typed capability refusal (`engine_capability_missing`, a member the Rust engine does not serve yet). `coordinator.ts` `finishUnpublishedFailure` charges each such refusal with `chargeCapabilityRefusal(requestId)`: under `PUBLICATION_CAPABILITY_ATTEMPTS` (3) claims it returns the claim to queued, so a consumer on an engine that serves the member can still publish it; on the last claim the write ends `failed` with the refusal, its stored detail adds `attempts` and `limit`, and the waiter's error (`service.ts` `writeResponse`) carries the capability as `reason` and the member in `detail`, so it never reads as `write_pending` and the writes behind it in its source go on. The count lives in the consumer process (bounded map, no column) and is dropped once the write ends in any terminal state (`settleCapabilityRefusal`, from `consumer.ts` `settled` and after the failed completion commits); a restarted consumer counts again from zero. A refusal in preparation ends failed on its first attempt. Pinned by `test/engine-parity/publication-retry-limit.test.ts` (an injected refusal on all three engines, and put_page over MCP on stdio and http) and `test/engine-parity/bench-save-repro.test.ts` (the real Rust refusals).
