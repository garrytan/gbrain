- `src/commands/doctor/checks/write-gate-holds-stranded.ts` — `write_gate_holds_stranded` (BRAIN, after `trust_release_unpreviewed_fields`, read-only). A held write (`write_gate_holds`) names its page only by `(source_id, slug)`, so a rename or delete can leave it naming a slug no live page has. Held rows in the selected sources (`doctorSourceIds`; an explicit empty scope reads nothing) whose slug has no live page are counted once each, in the first class that fits: `renamed` (the alias table or the rename history leads from the slug to a live page in the same source; "suspected", since history can name several destinations; warns, because that page's held text is no longer hidden), `page_deleted` (the page or the rename destination is soft-deleted) and `no_page` (no page and no rename record, for example a write held before its page exists); the last two are `ok` with `severity: info`. The message says plainly that the check detects and does not fix the leak, and that neither release nor drop restores the quarantine on the renamed page or takes back delivered text; the one structured next action is the read-only `gbrain trust review`. Bounded: held rows are read in `(source_id, id)` keyset batches of 500 on the `(status, source_id, id)` index (id, kind, source and slug only), the 5000-row budget counts held rows before any slug, page or rename filtering, an extra-row probe tells a full read from a cut one, and the scan stops at `ctx.entryDeadlineAt` (else 10 s). A scan that stops early is `warn` with `details.health: unknown` and `reason: bound` (`bound: row_limit | deadline`), never ok. Before any read, one preflight asks which of `write_gate_holds`, `slug_aliases`, `slug_rename_history` and `pages` row-level security hides from the role (row security active and no permissive SELECT policy for it, the folder-access and writer-guard test); any hidden relation is `warn`, `health: unknown`, `reason: row_level_security`, `details.hidden_tables`, because a hidden table reads as zero rows, never an error. The candidate slugs of a batch (the hold's own, alias targets, history targets) are resolved first and `pages` is probed by its `(source_id, slug)` key. Per-source counts are built in a Map, so a source id such as `constructor` keeps its own entry. An unreadable or missing rename table, and any other read failure, is unknown through `checkError`. A raw-SQL refusal from an engine without raw SQL (`engine_capability_missing`, the Rust engine) is a named unknown (`reason: engine_capability_missing`); the scan helper catches nothing and the entry classifies what it throws, so the capability-refusal guard has nothing to baseline. A schema without `write_gate_holds` is `ok` (`pre_trust`). Test: `test/doctor-write-gate-holds-stranded.test.ts` (PGLite, and Postgres with `DATABASE_URL`).
