# Key files: Engines (2/2, purge)

[Subsystem index](../KEY_FILES.md) · [Previous entries](engines-2-more.md). Read only the entries relevant to your change.
Current behavior and load-bearing invariants; history belongs in Git and CHANGELOG.

- `src/core/engine-sql/page-purge-journal.ts` — the journal statements of a page purge's sweep and intent redaction (`persistence/intent-redaction.ts`), as typed engine members the Rust engine serves from its request, effect and counter records (`rust/docs/store/persistence.md`, "The page purge's journal statements"): `listRequestsForSlugs`, `readJournalCeiling`, `sweepJournalChunk` (one keyset chunk of the carrying predicate), `lockWriteRequests`, `readEffectBytes`, `redactWriteRequestRow` and `releaseTerminalBytes`. The two sweep reads run in write preparation, so they are in `TYPED_PREPARATION_READS` and end on the server at the claim's deadline.
- `src/core/engine-sql/purge-stores.ts` — the scrubs of a page purge's retrieval stores, name stores and query cache, as typed engine members (`rust/docs/store/eval_capture.md`, "The page purge's retrieval, name and cache scrubs"): `deletePurgedFeedbackRows` (the retrieval event, link event, rating and weight deletes and the `eval_candidates.retrieved_slugs` rewrite of `scrubPurgedSlugs`, five counts keyed as the purge receipt names them), `deletePurgedNameStoreRows` (the volunteer log and gazetteer of `scrubPurgedNameStores`) and `clearQueryCache` (null when the table is missing; `clearRebuildableCache` sends only `query_cache` here). The Rust engine runs the eval candidate scrub in its store and answers 0 for the stores it does not keep. `purgeStoreScrubber(tx)` adapts a raw transaction for the engines' own purge SQL (`engine-sql/pages.ts`). `relationExists` stays raw SQL.
- `src/core/engine-sql/origin-holds.ts` — the statements of a derived-origin purge's parks and owed-purge records, as typed engine members the Rust engine serves from its page records and op checkpoint rows (`rust/docs/store/label_door.md`, "The purge's origin parks and owed-purge records"): `listPurgeOrigins` (the in-purge recheck's read of the origins among the ids, bounded like the carry's other origin reads), `upsertDerivedOriginPark` (a re-park keeps the owner request an earlier park held), `recordOwedPurgeRows` (the owed record and the hold's tombstone binding, rows written per record) and `deleteOriginHoldRows` (the park or owed rows of pages; only those two ops). `persistence/derived-origin-hold.ts` `parkDerivedOrigin`, `recordOwedPurge`, `clearOwedPurges` and `clearDerivedOriginParks` take the members instead of a raw engine. They run through `executeRaw` on the handle given, so inside a purge transaction they join it. The reads and prunes of the same rows (`readDerivedOriginParks`, `pruneDerivedOriginParks`, `readOwedPurges`, `pruneOwedPurges`, `releaseStaleHolds`) stay raw SQL. Pinned by `test/engine-parity/page-purge-holds.test.ts` and `rust/crates/gbrain-store/tests/page_purge_holds.rs`.
