- `src/core/search/keyword-or-rarity.ts` — rare words first in both engines' keyword OR retry. For at most `RARITY_MAX_KEYWORD_TERMS` (12) words (the title arm keeps `RARITY_MAX_TERMS` = 4: it runs one statement per word), `rareTermPagesSql` reads the pages of each word's first `RARE_TERM_CHUNK_CAP` + 1 visible chunks (brain-wide, weights only; stopwords and, on Postgres, words `commonOrTokens` in keyword-or-narrow.ts estimates past the cap are skipped); a fitting word weighs 1 / pages. `rankOrFallbackByRarity` re-runs the retry with the rarest words' OR and sorts by summed weight.
- `src/core/search/keyword-identifier-probe.ts` — #7491: `keywordArmRows` builds both engines' `searchKeyword` rows from the strict rows. With `orFallback`, offset 0 and no quote or negation, a query naming an identifier (`identifierTokens`: a hash number `#412`, or a token `identifier-query.ts` recognizes: a 6+ digit run, hex id, code, email, URL or phone) and other words runs the arm's own statement once more with the AND of the identifier tokens as the match query and the any-word query as the rank query: same scope, visibility, chunk predicate, filters and candidate cap as strict. Its rows are untagged (they vote like strict rows): after the strict rows when strict matched, ahead of the relaxed rows (`keyword_relaxed`) when it did not; one row per page, cut to the limit. A failed probe adds nothing. `holdsIdentifiers` lets the title arm's OR retry (`engine-sql/titles.ts`) lead with, untagged, the titles holding every identifier. Pinned by `test/search/identifier-probe.serial.test.ts` (+ Postgres E2E) and `test/search/keyword-identifier-probe.test.ts`.
- `src/core/search/keyword-handles.ts` — GBRA-108: `slugHandles` finds the query's slug handles (a hyphenated slug-leaf token with a letter, bare or quoted on its own, at most `MAX_SLUG_HANDLES` = 16; a query with a negation or a longer quoted phrase resolves none, and the strict match (`slugHandles(query, true)`) resolves them only when every term is a handle or `OR`). A failed handle or identifier-probe read adds no rows and calls `SearchOpts.onKeywordIncomplete` (`keyword_candidates_incomplete`, reason `timeout` or `provider_error`). They resolve by exact slug basename (`handleMatchSql`, served by `idx_pages_slug_basename` like `whois`) as an arm of the keyword statement (`search/keyword-statement.ts`) under its filters, scope and visibility, so `--types`, granted sources, private pages and quarantine apply. `match: "keyword"` lists and counts the named pages first; in `searchKeyword` (orFallback, offset 0) `keywordArmRows` puts them ahead of every other row, untagged. A query without a handle builds the statements it built before. Pinned by `test/search/slug-handles.serial.test.ts` (+ Postgres E2E) and `test/search/keyword-handles.test.ts`.

- `src/core/search-vector-backfill.ts` — keyset-batched rebuilds of stored keyword vectors, shared by `reindex-search-vector` (every row) and the `fts_cjk_boundary` migration (an optional `where` limits it to rows with a CJK boundary). `backfillChunkVectors` recomputes `content_chunks.search_vector` with `chunkSearchVectorSql`; `backfillPageVectors` (#6374) reads each batch through an UPDATE-to-self of `id` (`RETURNING id, slug, source_id, timeline, knowledge_revision` plus whether a `fact_withdrawals`/`fact_purges` row covers the page or its whole source), takes the seal's effective timeline (the raw column, or for a withdrawn/purged page `readPageSnapshot`'s overlaid timeline, so a database withdrawal never returns to the vector), sanitizes it with `sanitizeRemoteBody` as the seal does, and writes `search_vector` through `pageSearchVectorSql` in one `UPDATE … FROM unnest(…)` guarded by the revision read (a page edited in between is skipped; its seal reindexes it). Each statement scans at most `BACKFILL_RANGE` (50 000) ids past the cursor and rebuilds at most `BACKFILL_BATCH_SIZE` (5000) of them, never one transaction; the cursor advances to the range end even when nothing matched (so a filtered run on a brain with no CJK text never scans the whole table in one statement), and the run stops at the max(id) the first batch read; the cursor persists after every batch under `backfill.<checkpoint>.last_id` and the caller clears it. Pinned by `test/reindex-search-vector.serial.test.ts`, `test/reindex-search-vector-pages.serial.test.ts`, `test/fts-cjk-boundary.test.ts`, `test/search-vector-backfill-withdrawal.test.ts`, `test/search-vector-backfill-range.test.ts`. FTS write expressions (`src/core/fts-language.ts`, #6370): `FTS_INPUT_FUNCTION_SQL` (`gbrain_fts_input(text)`, IMMUTABLE STRICT PARALLEL SAFE, `search_path = pg_catalog`: two `regexp_replace` passes built from `CJK_SLUG_CHARS` that insert a space at every CJK→ASCII-alnum and ASCII-alnum→CJK boundary; a byte-for-byte no-op without CJK, idempotent; spliced into src/schema.sql by `build:schema`), `FTS_CJK_BOUNDARY_REGEX` (the rows the `fts_cjk_boundary` migration rebuilds), `pageSearchVectorSql` (the sealed page vector used by the seal, the import seal and `search-vector-backfill.ts`), `chunkSearchVectorSql`, and `pageSearchVectorTriggerFnSql`/`chunkSearchVectorTriggerFnSql` (the two trigger functions under a language, byte-identical to src/schema.sql's for `english` so the blob replay after a migration leaves the catalog unchanged; used by `reindex-search-vector` and the migration). Every indexing `to_tsvector` reads through `gbrain_fts_input`; `applyFtsLanguagePolicy`'s `to_tsvector('english',` prefix rewrite still matches. Pinned by `test/fts-cjk-boundary.test.ts`, `test/fts-cjk-boundary-search.test.ts`, `test/e2e/fts-cjk-boundary-postgres.test.ts`.
