- `patches/postgres@3.4.9.patch` — auditable delta for the driver ownership and cancellation repair already applied to the shipped `vendor/postgres` ESM/CommonJS/workerd source (not an install hook; `bash vendor/update-postgres.sh --check` verifies it), consumed by `PostgresEngine.runUnsafe` through `#postgres`. Abortable reservations settle atomically; shared transaction queues isolate cancellable SQL from tagged/savepoint siblings while preserving unfenced pipelining. A pooled connection (pool `max` above 1) or a released reservation whose last ReadyForQuery status is not idle is terminated instead of reused, and the `onpoisoned(status)` option reports it (pinned by `test/e2e/postgres-poisoned-connection.test.ts`). See [PostgreSQL cancellation ownership](../postgres-cancellation.md) for settlement, deadline, transport and clean-install invariants. Pinned by `test/e2e/persistence-chaos.test.ts`. The patch also shares each pool's described parameter types across its connections (`shared_types`; `db.resolveSharedTypes()` reads the `GBRAIN_PG_TYPE_CACHE=0` kill switch at the four pool construction sites, `db.clearSharedTypes()` runs after `initSchema` applies migrations), so a first run on another connection, and every run under `prepare: false`, skips the describe round trip; pinned by `test/e2e/postgres-shared-types.test.ts`. #6355: `closed()` settles a startup's internal query (the array-types fetch) and clears its saved error before reconnecting for `initial`, so a backend terminated during startup neither hands the caller's first statement a stale `57P01` on the fresh connection nor leaves an unhandled rejection (`fetchArrayTypes` also swallows its own failure); it clears the pending write buffer and its immediate handle, so a close that catches a buffered statement does not leave the next StartupMessage appended and unscheduled (a pool slot stuck at `CONNECT_TIMEOUT`); pinned by `test/postgres-driver-startup-death.test.ts` against a scripted wire-protocol server. A query cancelled after it was written stays current until its own ReadyForQuery, so its answer is never read for the next query, and rejects `57014`; no server cancel is sent for it while statements are pipelined behind it, because a CancelRequest stops whatever the backend is running (pinned by `test/e2e/postgres-driver-cancel-pipeline.test.ts`, direct and PgBouncer). A statement answer that arrives with no current query retires the connection with `CONNECTION_DESYNC` and calls `ondesync({ message, connection, statement })`; `PoolIncidentCounter` logs `pg_connection_desync` (pinned by `test/e2e/postgres-driver-desync-tripwire.test.ts`). #6930: `array_types` hands every pool for one database target the array types the process's first connection fetched, so later connections skip the pg_type round trip; `transaction_pipeline` pipelines on a connection its owner holds (`sql.begin`, `sql.reserve`) while every statement in flight leaves it inside a transaction and never behind COMMIT/ROLLBACK/END/ABORT/PREPARE TRANSACTION, so a transaction-mode pooler URL (`max_pipeline` 0, `db.transactionPipelineOptions`, `GBRAIN_PG_TXN_PIPELINE=0` off) keeps #6543's boundary; pinned by `test/pathological/pg-round-trips-6930.test.ts` and `test/e2e/pgbouncer-transaction-pipeline-6930.test.ts`. GST-2260: the first `RevalidateCachedQuery` error (0A000: a prepared `SELECT *`/`RETURNING *` whose table changed) bumps a process-wide plan generation, so every connection drops its prepared statements before its next query: one failure per process per migration, not per pooled connection (`test/stale-plan-heal.test.ts`).

- `src/core/engine-sql/` — one SQL implementation per migrated storage domain (the domains are the `migrated` rows of `scripts/engine-sql-baseline.tsv`), run by both engines through one executor contract:

  ```
  PGLiteEngine / PostgresEngine   one-line delegations; RLS scoping per method as on master
        | get engineSql()         fresh adapter per access, never stored (transaction clones)
        v
  engine-sql/<domain>.ts          Postgres master text; sqlFragment composition; capabilities
        |  ScopedRead / LegacyUnscopedRead brands (brands.ts), row kinds (normalize.ts)
        v
  engine-sql/executor.ts          SqlExecutor: query/run, executeRaw, unsafe, transaction; {rows, affectedRows}
        |
        +--> dialect-pglite.ts    db.query on the engine's cached, checkpoint-guarded handle
        +--> dialect-postgres.ts  runUnsafe(conn, sql, params, {signal?, prepare: true, simple: false}); no gauge
  ```

  Outside `engine.transaction()`, `engineSql` hands engine-sql `guardedHandle` (`src/core/pglite-engine/checkpoint-guard.ts`): WAL-writing statements take `runStatement`, executor transactions `runOutermost`, like `executeRaw` and `transaction()`. Before that, engine-sql autocommit writes such as `markPagesExtractedBatch` never probed WAL; past the automatic trigger (about 528 MB with max_wal_size 1 GB) the crossing UPDATE ran the checkpoint inline and spun forever (GBRA-69). Pinned by `test/pglite-checkpoint-guard.test.ts` and `test/fixtures/pglite-engine-sql-wal-worker.ts`.

  Inputs engine-sql never resolves arrive already resolved: source scope (`sourceIds` > `sourceId` > `'default'`), the registry-active embedding column (bare name, quoted with `quoteIdentifier`), page-state guards as callbacks (`lockPageKeys` / `readPageSnapshot`) and the engine's `transaction()` where master used it. A read master ran inside `withScopedReadTransaction` keeps that literal call in the engine method (the RLS AST inventory counts direct sites) and brands the tx handle's executor: `scopedRead(this.engineSqlOn(tx))` on Postgres, `scopedRead(this.engineSql)` on PGLite.

  `fragment.ts` numbers placeholders at render time, so text is byte-identical to the tagged templates it replaced (`test/fixtures/goldens/sql-text/`). Capabilities (`maxBindParamsPerStatement`, `transactionAdvisoryLocks`, `probesEmbeddingCast`) carry the real engine differences; `docs/designs/refactor-wave-1/w1-inventory.md` classifies every method. Page-state orchestration stays in the engines: `putPage`'s transaction, page-key lock and revision check, and the `updateSlug` / `setPageAliases` transactions, call `pages.ts` on the transaction clone's executor; `getPage` / `readPageSnapshot` keep their SQL in `page-state/snapshot.ts`. Reads with an early return that must not open a scoped transaction (`listPrefixSampledPages`, `listCorpusSample`) take a `ScopedReadRunner`. Nothing here imports an engine façade (`check:layering`); SQL may splice only constant text (`check:engine-sql-dynamic`); brands are unforgeable (`check:engine-sql-brands`); engine SQL only shrinks (`check:engine-sql-ratchet`). Tests: docs/TESTING.md "Engine-sql".
