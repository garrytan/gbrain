- `src/core/search/connection-budget.ts` — per-op pooled-connection budget for `search` and `query`. `SEARCH_CONNECTION_LIMIT` (4) is the most connections one op holds at once. `withSearchConnectionBudget` opens the scope; the ops' `metered` wrapper in `src/core/ops/search.ts` and `dispatchToolCall` (`src/mcp/dispatch.ts`, so pre-op reads and the response-meta hook count too) both enter it, and a nested call shares the enclosing budget. `holdSearchConnection` is called at the engine's connection seams, `PostgresEngine#transactionOn` (a top-level transaction, held until its COMMIT settles even when a read transaction answers early), `executeRaw`'s JIT-off and statement-timeout envelopes (which reserve their own connection) and `runUnsafe` (one statement). A read whose `signal` aborts while it waits for a slot leaves the queue and rejects `AbortError`. Work inside a held slot runs outside the scope, so statements on a transaction's own connection never wait on a second slot. A read started under `withUrgentSearchConnections` (hybrid search's lexical, relational and vector arms, `hybrid/arms.ts`) takes the next free slot ahead of waiting ordinary reads (the keyword count and entity resolution an op starts early for its response; GBRA-156, `test/search-connection-budget-urgent.test.ts`). Outside a scope, and on PGLite, nothing waits. These reads use the ordinary read pool (the transaction pooler behind a split route), never the direct/session lane. Pinned on Postgres at the wire by `test/e2e/search-connection-budget-postgres.test.ts`.

The Rust engine serves it from the stored request rows (`rust/docs/store/persistence.md`). Pinned by `test/engine-parity/persistence.test.ts`.
- `readCounterRows` and `readAdmissionRate` (in `src/core/engine-sql/persistence-journal.ts`) — the two reads the write-capacity checks make. `readCounterRows(keys)` returns the existing `persistence_counters` rows for the keys in byte order (`COLLATE "C"`), unlocked and without creating any; `persistence/journal.ts` `assertWriteHeadroom` and `readOutstandingRoom` call it. `readAdmissionRate(principal | null)` returns the brain's first request id and the admission sample of the latest 1000 requests (of the principal, or of the brain when null): count, age in seconds, mean terminal reservation and mean compacted receipt size; `persistence/limits.ts` `oneYearCapacity` calls it once per refusal and uses its cached rates only when the first request id still matches. The Rust engine serves both from the counter and request rows (`rust/docs/store/persistence.md`). Pinned by `test/engine-parity/persistence.test.ts` and `test/engine-parity/persistence-declaration.test.ts`.
- `ownsSchemaTables` (in `src/core/engine-sql/persistence-journal.ts`) — whether the connection's role is a member of the
role that owns
the `sources` table (`pg_has_role(current_user, relowner, 'USAGE')`); a missing table or answer reads as owner. `persistence/schema-admission.ts` `schemaAdmissionRefusal` calls it only when the schema is behind, to pick the fix actor of a `migrations_pending` refusal (`agent` when the role owns the tables, else `host_admin`). The Rust engine answers `true` (`rust/docs/store/journal.md`). Pinned by `test/engine-parity/persistence-declaration.test.ts`.
- `readOAuthClientWriteGrant`, `readAccessTokenWriteGrant`, `shareLockWriteCredential` (in `src/core/engine-sql/persistence-journal.ts`) — the credential reads `persistence/authority.ts` `authorizeWrite` re-checks a write against: the owning OAuth client's live grant row (`deleted_at`, `scope`, source, operation, slug, tool and delegated-namespace columns), the owning legacy token's grant row (the `TOKEN_GRANT_ROW_COLUMNS` this brain's `access_tokens` has, probed from `pg_attribute`, plus `revoked_at`; named columns because a cached `SELECT *` plan fails 0A000 after a migration), each null when the row is missing, and `lock` holds the row `FOR SHARE` so a revocation commits before or after the publication. `shareLockWriteCredential` takes that share lock alone before an attested write re-reads its attest right (GST-1113). Decisions stay in `authorizeWrite`; its per-check memo (`onceReads`) answers a plain grant read once and always runs a locking one. The statement deadline bounds all three. The Rust engine answers null and locks nothing: it keeps no OAuth clients or tokens (`rust/docs/store/journal.md`). Pinned by `test/engine-parity/persistence-declaration.test.ts` ("a write owned by an OAuth client or legacy token with no live grant refuses permission_denied") and `test/qm-scope-writes.test.ts` (the attest-sources removal that lands before the lock).
- `listHostConsumerRows`, `probeLiveConsumerRows`, `renewConsumerRow`, `deleteConsumerRow`, `stampWorktreeHeartbeats` (in `src/core/engine-sql/persistence-claims.ts`) — the consumer heartbeat rows in `persistence_consumers`: the host's rows oldest first, the host's live full rows of the resident kinds other than the caller's, the renewal (which purges the host's lapsed rows in the same statement), the row delete on stop, and the stop-time stamp on the host's worktrees. The SQL text is the one `persistence/consumer-heartbeat.ts` ran through `executeRaw` / `executeRawDirect`. On Postgres the renewal, delete and stamp run on the direct pool; the two reads run on the direct pool when `direct` is set, which `consumer-election.ts` passes while the consumer's route is direct (`consumerOnDirectLane` in `persistence/consumer-lane.ts`). The two reads take the per-statement bound in `statement-deadline.ts`. The Rust engine keeps no consumer rows (one process owns its brain): the reads answer none and the writes change nothing (`src/core/rust-engine/store-members/persistence.ts`). Pinned by `test/engine-parity/persistence.test.ts`, `test/persistence-consumer-election.test.ts` and `test/e2e/persistence-consumers-postgres.test.ts`.
