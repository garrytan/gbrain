- `src/core/rust-engine.ts` + `src/core/rust-engine/` — the opt-in Rust engine shell (ENGINES.md "The Rust engine shell"). `openRustEngine({ addon, databasePath })` is the one seam the addon loader calls after it has loaded and verified the native addon; it returns a `RustEngine` (every `BrainEngine` member except `kind`, which is `'rust'`; `BrainEngine.kind` admits it once the `rust` config value lands; D18) that keeps the addon handle and store path and owns the lifecycle: `connect` records the config, runs the owner election (`owner-ipc/election.ts`, below; `ownerRole` is `'owner'`, `'client'` or null before `connect`) and, as the owner, opens the store (`rust-engine/store.ts` `openRustStore`: one napi `Pool` and `Brain`, opened with `LATEST_SCHEMA_VERSION`), `disconnect` runs the `registerBeforeDisconnect` stops, waits for an open still in flight to settle (it closes its own store and leaves its role), stops the owner server, closes the store and releases the owner lock last, even when a close fails, then rethrows that error (a client only closes its connection), `reconnect` does both. Members in `STORE_MEMBERS` are installed as async wrappers that run on the open store (`storeFor(member)` waits for an open in progress on the owner, then `openStore(member)` throws `engine_closed` when not connected); every other `BrainEngine` member is installed from the prototype loop and refuses `engine_capability_missing` (reason = `rustMemberCapability(member)`, detail `member=… capability=… outcome=none written=nothing`) before any work. `rust-engine/members.ts` (`RUST_ENGINE_MEMBERS`, `satisfies Record<keyof BrainEngine, MemberClass>`) classifies every member, so a new engine method fails typecheck until it is classified. `rust-engine/errors.ts` (`capabilityMissing(capability, member, outcome)`) builds the refusal. `src/core/sql-engine-kind.ts` (`EngineKind`, `isSqlEngineKind`, `isRustEngineKind`, `sqlEngineKind(kind, member)`) narrows a kind for SQL-only code and refuses `raw_sql` for Rust; `page-body/limits.ts` `stageBatchBytes(kind)` uses it. each is `(brain, ...args)` and returns what the PGLite member returns. `common.ts` `takeOptions` forwards only the options the store keeps, skips the listed ignored ones, and refuses any other defined option with `engine_capability_missing` (`capabilityMissing`, written=nothing) instead of dropping it, so a caller never gets a quiet partial answer. `store-codec.ts` converts the store's rows to the engine types (ISO strings to `Date`, `has_embedding` to `embedding_is_null`, a timeline `date` to midnight UTC, extra store fields removed). `store-errors.ts` `mapStoreError` maps store error codes: `store_closed` to `engine_closed`, `store_locked` to `rust_store_locked`, `format_unknown`, `store_corrupt` and `store_io` to `rust_store_unreadable`, `revision_conflict` and `revision_required` to `PageRevisionConflictError`, `page_not_found` to the error PGLite throws for that member. `store-capabilities.ts` `servedCapabilities()` reports a capability only when every member of it is in `STORE_MEMBERS`. - `src/core/rust-engine/owner-ipc/` — the owner protocol of the Rust engine (ENGINES.md "The Rust engine shell"; design in `docs/designs/RUST_ENGINE.md`). One process owns a brain: `election.ts` `electOwner` takes the kernel lock `<database_path>.gbrain-owner.lock` and the owner serves its engine on `<database_path>/.gbrain-owner.sock` (`server.ts`: 32 calls at once, the rest in a FIFO queue of at most 1,024 calls, at most 256 MiB of call frames held at once (queued and running), at most 256 connections, each over a bound refused `owner_busy` with reason `queue_full`, `inflight_bytes` or `connections`; a refused connection gets one `refused` frame and is half-closed, a refused peer that never closes its side is cut off after 1 second (`OWNER_IPC_REFUSED_DRAIN_MS`), and past 64 refusals in flight the next is dropped with no frame; a cancel frame ends a call, `deadline_at` and `read_deadline_at` bound it; where the kernel gives a peer's uid (`cli-socket/peer-cred.ts`) a connection from another OS user gets a `refused` frame `owner_ipc_peer_refused` reason `peer_uid` and nothing runs); every other process becomes a client (`client.ts` `installOwnerClient`, never opens the store, capabilities mirror the owner's hello; before it connects it refuses a socket file another user owns, `socket_owner`, or one with group or other permission bits in a directory others can enter, `socket_mode`, and after it connects an owner of another uid, `peer_uid`; for a remote caller, `callerIsRemote`: an MCP request marked by `src/core/remote-caller.ts`, a job whose submission authority is not the application, or a remote verified writer, it sends only the reads of `routes.ts` `OWNER_IPC_REMOTE_READS` and refuses any other member `engine_capability_missing` with nothing sent) or, after 5 seconds, throws `owner_unavailable` with reason `not_sent`. `routes.ts` classifies each member: `local` (`kind`, `capabilities`, `connect`, `disconnect`, `reconnect`, `registerBeforeDisconnect`), `refuse` (`transaction`, `transactionDirect`, `withReservedConnection`, `holdSchemaMigrationLock`, `keywordBoundedRead`; against a Rust owner all but `holdSchemaMigrationLock` first meet the capability check below and refuse with the owner's own reason, `transactions` or `raw_sql`; `holdSchemaMigrationLock` and a call whose arguments hold a function other than a search metadata hook refuse `engine_capability_missing` with `via=owner_ipc`) or `forward` (everything else; a member the owner's hello lacks, and the store does not serve, refuses at the client as the owner's own engine does). `whole-op.ts` and `owner-ops.ts` forward `importFromContent`, `importFromFile`, `importImageFile` and `importManagedFiles` as one request that runs, transaction included, in the owner; paths are made absolute, and a remote caller or a function option refuses. `protocol.ts` and `codec.ts` frame the calls (an owner reply over 128 MiB ends `response_too_large`; a call's `access` field carries the caller's access record, which the owner runs it under; `deadline_at` ends a queued call `timeout` reason `not_started` and a running one `outcome_unknown`; `timer.ts` `setDeadlineTimer` re-arms past the 2^31-1 ms setTimeout limit on both sides, so a far deadline waits instead of firing at once; frame rules refuse `owner_ipc_protocol`: a hello of another version (the owner sends its hello, then closes; the client's connect rejects `version_mismatch`, which the election does not retry), a call before the hello (`hello_missing`), an id still open on the connection (`duplicate_id`, the first call keeps its cancel and close abort), arguments that are not a list (`args_not_array`), and an answer the client cannot decode (`result_undecodable`, that call only); the socket directory and lock path resolve symlinks, so every alias of one brain names one owner). When the owner exits, a call in flight ends `owner_unavailable` with reason `outcome_unknown`; a RustEngine client (`installOwnerClient`'s `rejoin`, `RustEngine._takeOver`, which shares the open's single flight) runs the election again on its next call and becomes the owner, opening its store, or a client of the new owner, so the call works with no restart; a whole operation that finds this process became the owner ends `not_sent` and its retry runs in process. A client installed without `rejoin` answers later calls `not_sent`. Pinned by `test/rust-owner-ipc.test.ts` (child processes from `test/helpers/owner-ipc-child.ts`), `test/rust-owner-ipc-frames.test.ts`, `test/rust-owner-ipc-limits.test.ts`, `test/rust-owner-ipc-peer.test.ts` and `test/rust-owner-ipc-remote.test.ts`.
- `src/core/remote-caller.ts` — `withRemoteCaller(remote, fn)` / `isRemoteCaller()`: an AsyncLocalStorage flag `src/mcp/dispatch.ts` sets around every operation handler (`ctx.remote !== false` is remote), so code below the handler (the Rust owner client) can tell an agent-facing caller from the trusted local CLI without threading the context through. - `src/core/rust-engine/addon-loader.ts` — the Rust engine addon loader (ENGINES.md "The Rust engine shell"). `loadRustEngineAddon(overrides?)` returns `{ ok: true, addon }` or `{ ok: false, code, reason, message }` for the two refusals and rethrows anything else; `loadRustAddon` is the throwing form. Order: `GBRAIN_RUST_ENGINE_ADDON` (an absolute path to a `bun run rust:build` file; skips only the release checksum pin, `engine_abi` and target are still checked); then the addon at `<gbrain home>/engines/rust/<engine_build>/<target>.node` named by the cached `manifest-<version>.json` of the running version, loaded only when its SHA-256 equals the manifest's. It never reaches the network, takes no lock and writes nothing; a refusal leaves every file as it was. Only the Rust engine's open path may import the loader, lazily, so PGLite and Postgres brains never load the addon or create `<gbrain home>/engines/`; it loads with `process.dlopen` from a computed path (a literal `require` of a `.node` would be bundled into compiled executables). Reasons (`addon-errors.ts`, listed in `error-registry.ts`): `rust_engine_addon_missing` is `unsupported_target`, `not_installed` or `override_not_found`; `rust_engine_addon_mismatch` is `digest`, `engine_abi`, `engine_build`, `target` or `load_failed`; both are raised before the brain is touched. `addon-manifest.ts` parses the manifest and holds `RUST_ENGINE_ABI` and `RELEASE_ADDON_TARGETS` (`linux-x64-glibc`, `darwin-arm64`); `addon-target.ts` names this platform's target. The addon itself (`rust/crates/gbrain-napi/src/binding.rs`) refuses a typed array whose buffer the runtime (`napi_is_arraybuffer`) does not call a plain `ArrayBuffer`, so hiding `SharedArrayBuffer` or swapping a prototype changes nothing. Pinned by `test/rust-engine-addon-loader.test.ts` and `rust/smoke/smoke.test.ts`.
