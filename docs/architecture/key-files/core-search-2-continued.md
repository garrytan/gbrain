Current behavior and load-bearing invariants; history belongs in Git and CHANGELOG.

- `src/core/search/rank-priors.ts` — `applyRankPriors`: multiplicative priors after rerank and pinning (person rows on an organization question, low-coverage image rows stamped `image_page`, undated rows on a when-question, redirect stubs, and archive rows (GST-2768: ARCHIVE_PRIOR under a close non-archive row, ARCHIVE_HITS_PER_DAY per day, off for a conversation or date query)); each changed row carries `rank_prior` and `rank_score`. Knob `search.rank_priors`.
- `src/core/search/score-contract.ts` — `scoresFollowRank`: at the search/query op boundary the returned `score` follows the returned order (the rerank score, times any rank prior, in a reranked list; a running minimum otherwise) and the replaced value stays as `fused_score` (#7156).
- `scripts/bench/ranking-shapes/` + `test/fixtures/ranking-shapes/` — synthetic two-source ranking bench (208 pages, 70 questions): `run.ts` builds a PGLite brain, runs search/query/query --expand through a checkout's CLI behind a caching provider proxy and scores hit@k, MRR and per-shape checks (twins, stubs, families, priors, score order, chunk size).
- `src/core/search/vector-exact.ts` — opt-in exact vector scan on Postgres. `search.vector_exact_max_chunks` (whole chunks, 0 = off, file > DB via loadConfigWithEngine, read per search by hybrid `request.ts` into `SearchOpts.vectorExactMaxChunks`; `vectorExactMaxChunksValueProblem` backs the `config set` refusal). `PostgresEngine.searchVector` calls `searchExactFirst` before the index walk: it reads nothing when the setting is 0 and otherwise asks the engine's `contentChunkCountCache` (one `CONTENT_CHUNK_COUNT_SQL` reltuples read in flight, refreshed once a minute, waited on at most `VECTOR_EXACT_COUNT_WAIT_MS`; a slow, failed or never-analyzed count is unknown and skips the exact attempt). `searchExactWindow` runs `exactSql` bound at the candidate window (`VectorPoolAttempt.exactWindow`; the pool's unlimited exact fallback still binds NULL) under one `VECTOR_EXACT_BUDGET_MS` budget, widening a full window whose pages fall short x4 up to `VECTOR_EXACT_ESCALATIONS` times; rows answer when they fill the limit or the window was short; a 57014 timeout or spent budget returns null and the index path runs; other errors propagate. Doctor `vector_plan` reports the setting in `details.exact_scan` and notes when it covers the brain. PGLite and Rust ignore the option. Pinned by `test/search/vector-exact.test.ts` and `test/e2e/vector-exact-scan-postgres.test.ts` (sparse-graph fixture: exact equals the in-process truth unfiltered, source-scoped and with private and deleted pages excluded; off or below the ceiling equals the index path; an exact scan the server cancels at its budget falls back, also inside a caller transaction).
