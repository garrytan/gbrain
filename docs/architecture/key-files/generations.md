# Key files: Derived generations

[Subsystem index](../KEY_FILES.md). Read only the entries relevant to your change.
Current behavior and load-bearing invariants; history belongs in Git and CHANGELOG.

- `src/core/generations/{contract,plan,publish,proofs,config,repair,ledger-scrub}.ts` + `adapters/{page,atoms,index}.ts` (GBRA-161) — the generation primitive: one ledger row per derived key generation (`derived_generations`, items and bounded preimages in `derived_generation_items`); `publishGeneration` holds a shrunk, oversize, unproven-empty, valve or segmented result and otherwise writes, completes, rechecks, retires (versioned, stamped) and activates in one transaction. `gbrain repair generations` restores or releases from previews; doctor `generation_retirements` / `generation_held`. Reference: [generations](../generations.md). Tests: `test/pathological/g1-generations.test.ts`, `test/pathological/g1-atom-generations.test.ts`.
- `src/core/generations/fence-evidence.ts` (#8819) — `factsFenceHeld`: which positioned fact rows of a page some fence held at the same row number, claim and visibility (a non-retired item of any `fact_fence` generation of the page, the replaced body's rows from `pageFenceRowKeys`, which reads a segmented page from its marker segments, or a stored `page_versions` body, newest first, at most 1000; `complete` is false past that or when a version has no body, as a segmented snapshot has none). The page projection (`projectFactFenceGeneration`, which returns `retireIds` and `kept`) retires only held rows, rows whose claim the incoming fence states, and conversation-extractor rows a fence row displaces; the managed `extract_facts` reconcile keeps the other unheld stale rows out of its retirements. `moveKeptRows` moves a kept row whose number an incoming fence row claims above every row of the page. The projection's evidence is also why `canonical-projections.ts` reads the prior fence before publication. Tests: `test/fence-first-generation-8819.test.ts` (PGLite and Postgres).
- `src/core/repair/unwithdrawn-facts.ts` — `gbrain repair unwithdrawn-facts` (#8819), explicit-only and preview-bound. `classifyUnwithdrawnFacts` (read-only; also the doctor check's count) takes each fact a `fact_fence` generation retired (a `retired` ledger item with a fact preimage that was active and positioned) whose row is still as the retirement left it (expired at the generation's instant, `row_num` NULL, same claim and visibility; conversation-extractor rows excluded), and classes it `evidenced` (no fence ever held it: `generations/fence-evidence.ts` over the ledger, the current page and its stored versions), `ambiguous` (`version_history_gap_at` set, or versions left unread) or `excluded:<reason>` (page missing, superseded, withdrawn, changed since retirement, `fence_held`, active duplicate at any visibility, duplicate candidate, `unmanaged_reconcile` on an unmanaged brain, whose reconcile would retire a restored row again). The preview saves one item per page with its revision through `preview-approval.ts`; the apply restores the preimage's lifecycle (`expired_at`, `valid_until`, `superseded_by`, consolidation marks) on the same id at its recorded row number when free, else above the page's rows, after reclassifying under the page key: managed, one database-only `managed_maintenance_restore_unwithdrawn_facts` request per page bound to the previewed revision (`prepareUnwithdrawnFactsRestore`, refusing `revision_conflict`); unmanaged, a page-locked `maintenanceTransaction` that refuses a changed revision and reclassifies (so restores nothing). Doctor `unwithdrawn_facts` (`commands/doctor/checks/unwithdrawn-facts.ts`). Tests: `test/repair-unwithdrawn-facts-8819.test.ts` (PGLite and Postgres).
- `src/commands/doctor/checks/unwithdrawn-facts.ts` — doctor `unwithdrawn_facts` (#8819): counts those retirements by class through `classifyUnwithdrawnFacts` (`excluded` reported, never a finding) and names the `gbrain repair unwithdrawn-facts` preview. Read-only.
- `src/core/generations/adapters/synthesis.ts`, `src/core/generations/synthesis-coverage.ts`, `src/core/generations/managed-retire.ts`, `src/core/cycle/synthesize-generations.ts` (GBRA-161 PR 4, #7065) — synthesis on the primitive: each re-synthesized transcript's outputs become its `synthesis` generation after postprocess; an earlier output retires (versioned, `synthesis-resynthesis`) only when it is an exact duplicate or the same subject with every claim, quote and citation covered (pure match in `synthesis-coverage.ts`); others stay live and `gbrain repair generations --kind synthesis --mode cleanup` lists and, on apply, retires them (`synthesis-cleanup`). A chunk failure, deferral or `generations.synthesis.retire_previous=false` makes the generation partial. Managed brains admit the activation plus one `managed_generation_retire` delete per retirement (`managed-retire.ts`). Reference: [generations](../generations.md#synthesis). Tests: `test/pathological/g4-synthesis-resynthesis-7065.test.ts`.
- `src/core/generations/adapters/single-page.ts` (GBRA-161 PR 5) — dream summary, `think` page and drift report as single-item generations: revision-bound, versioned first, restorable. Reference: [generations](../generations.md#single-page-kinds-and-fence-only-writers-pr-5). Tests: `test/pathological/g5-*` to `g7-*`.
- `src/core/engine-sql/derived-generations.ts` + `src/core/rust-engine/store-members/derived-generations.ts` + `rust/crates/gbrain-store/src/generations.rs` — the generation ledger statements of `src/core/generations/publish.ts` as engine members: `readLiveGenerationRow` (the live row and its owned items, behind `readLiveGeneration`), `activateGenerationRows` (supersede the live row, insert the new one with its ledger items, clear the key's held row and attempt counters, behind `activateGeneration`) and `recordHeldGenerationRow` (the same hold counts an attempt, another hold replaces it, behind `recordHeld`), and the rest of `publishGeneration`: `liveGenerationForOperation` (the identical-replay select), `countGenerationAttempt` and `clearGenerationAttempts` (the attempt counter behind `recordAttempt`), `readHeldGenerationContext` (behind `exhaustedHold`), `heldGenerationRowsForInput` (behind `heldForInput`), and `readGenerationValve` and `bumpGenerationValve` (behind `readValve` and `bumpValve`), and the consolidation adapter's `readGenerationRestored` (whether the live row restores another, behind `consolidationRestored`) and `clearTieHeldGenerationRows` (delete one entity's `tie` holds by owner-key prefix, behind `clearConsolidationTies`). These are ledger reads, not page reads, so they take no page read policy. Every engine refuses written JSON text (held context, proposal, completeness) that holds a number past the double range before it writes (`checkGenerationJsonNumbers`), since every reader would parse it to `Infinity`. PGLite and Postgres send the statements publish.ts always sent (the live items ordered by item key in byte order), on the engine's own `executeRaw`; publish.ts itself sends none. The Rust store keeps the rows under key tag `h` (reference: `rust/docs/store/generations.md`), so a fence publish and a whole `publishGeneration` run to the end on a Rust brain (pinned by `test/rust-derived-generations.test.ts` and `test/rust-generation-publish.test.ts`). The fact rows, take rows and extracted facts adapters (`generations/adapters/fact-rows.ts`, whose `readFactPreimages` in `engine-sql/facts.ts` reads the before-state (`FACT_PREIMAGE_SQL`) of named fact ids of one source in id order, and whose `restoreFactPreimage` writes one back: the strike, successor and consolidation columns, and the row number only when no other row of the page holds it, on the row of that id and source whose claim and visibility still match; `take-rows.ts`, whose before-state read is `readTakePreimages` in `engine-sql/takes-reads.ts`, and `extracted-facts.ts`, whose own-row read and retire are `listFactIdsBySourcePrefix` and `expireFactRows` in `engine-sql/facts.ts`) now run only typed members; the page adapters still run some raw SQL (see `generation-page-rows.ts` and `generation-atom-reads.ts` below), which the Rust engine refuses.
- `src/core/engine-sql/generation-ledger.ts` — the purge scrub of the generation ledger (`scrubGenerationLedger` in `src/core/generations/ledger-scrub.ts`) as two engine members: `scrubGenerationPageRows` (delete the page's held fence rows, null the purged item's preimages and every held proposal naming the page, drop the page's recorded fence blocks) and `scrubGenerationTextRows` (null the preimages, held proposals and contexts, and fence blocks whose lowered jsonb text carries a needle). Both return `{ derived_generation_items, derived_generations }`. ledger-scrub.ts keeps the needle preparation (lowercase plus the JSON-escaped form) and sends no SQL itself. Ledger reads, not page reads: no page read policy. The Rust store answers both from the `h` rows (pinned by `test/rust-generation-scrub.test.ts`).
- `src/core/engine-sql/generation-activations.ts` — the activation rows of `src/core/generations/managed.ts` (`derived_generation_activations`) as six engine members: `recordGenerationActivation` (record one activation's member rows; a repeated row is kept as it was), `markGenerationActivated` (point an activation at the generation it produced), `readGenerationActivationState` (the gate of `assertMemberPending`: the activation's state, its generation's state and the member's pending flag), `settleGenerationMember` (clear a member's pending flag), `listPendingGenerationMembers` (members whose generation is live and still pending) and `listGenerationOrphanCandidates` (members of a pending activation whose page is live, no unfinished write request names the activation, and no live generation of the same kind owns the page). The generation key lock of an activation is `lockGenerationKey`. Every engine refuses an activation id that is not a UUID before it writes (`checkActivationId`), because the orphan list casts each id to `uuid`. These are ledger reads, not page reads, so they take no page read policy. PGLite and Postgres send the statements managed.ts always sent, ordered text by bytes (`COLLATE "C"`, with the activation id as the orphan list's last tie-break); managed.ts itself sends none. The Rust store keeps the rows under key tag `h` (`rust/crates/gbrain-store/src/generations/activations.rs`), so a managed publication runs to the end on a Rust brain (pinned by `test/rust-generation-managed.test.ts`).
- `src/core/engine-sql/generation-repair.ts` — the reads of `src/core/generations/repair.ts` (`gbrain repair generations`) as six engine members: `readGenerationItemsByIds` (the ledger items of a live generation and its predecessor, behind the restore plan), `listUnmatchedGenerationRows` (live generations whose completeness lists earlier outputs left live unmatched), `listRestorableGenerationRows` (each live generation with the superseded generation it replaced), `listHeldGenerationRows` (held rows with the length of their retained proposal), `readHeldGenerationProposal` (the proposal a release-held apply rereads) and `listGenerationSourceIncarnations` (the source incarnations the preview hash binds). The three lists take a typed filter (`runId`, `since`, `ownerKey`, `id`): each present field is one literal SQL fragment, composed in the order the old `selectorSql` used, so PGLite and Postgres send the statements repair.ts always sent, with the same parameters and a total row order that sorts text by bytes (`COLLATE "C"`, as PGLite and the Rust store sort it), for every combination. `since` must be an ISO 8601 instant with a zone; every engine binds it as `YYYY-MM-DDTHH:MM:SS.ffffffZ` (`repairSinceInstant`) and refuses any other text. These are ledger reads, not page reads, so they take no page read policy. The Rust store applies the same filter to its rows (`rust/crates/gbrain-store/src/generations/repair.rs`); `listGenerationSourceIncarnations` composes `readSourceIncarnation` there. Pinned by `test/rust-generation-repair.test.ts` (all 16 combinations on three engines).
- `src/core/engine-sql/generation-fence-evidence.ts` — the statements of `src/core/generations/fence-evidence.ts` (#8819, whether a page's facts fence ever held a fact row) as four engine members: `listRecordedFenceItemKeys` (the fence item keys a fact_fence generation of the page, not held, records without retiring), `hasBodylessPageVersion` (whether a stored version has no body, as a segmented page's do, which leaves the evidence incomplete), `listFenceVersionBodies` (one batch of the stored versions whose body or timeline carries a facts fence marker, below an id, newest first) and `moveKeptFactRows` (the kept rows a fence row's number claims move above the page and the claims). PGLite and Postgres send the statements fence-evidence.ts always sent, with the same parameters and a total row order that sorts text by bytes (`COLLATE "C"`, as PGLite and the Rust store sort it); the move runs on the caller's transaction engine. These are evidence reads of one page, not caller page reads, so they take no page read policy. The Rust store serves them from its ledger, version and fact rows (`rust/crates/gbrain-store/src/generations/fence_evidence.rs`, `facts/kept_rows.rs`). Pinned by `test/rust-generation-fence-evidence.test.ts`.
- `src/core/engine-sql/generation-atom-reads.ts` — the atoms adapter's reads as three engine members. `readAtomOriginInput` is `atoms.ts` `readInput`: the live origin page's id, content hash, knowledge revision and size (`body_bytes` for a segmented page, the byte length of the two body columns for an inline one). `listProducerVersionRows` is `page.ts` `pageVersionEvidence`'s read: the saved `page_versions` of the listed slugs that one producer wrote (only `extract_atoms`; any other producer refuses on every engine), with the live page's visibility; `page.ts` `versionEvidence` then matches identity hashes. `listAtomWriteReceipts` is `atoms.ts` `receiptEvidence`: the content of committed `managed_atom_page` write requests whose activation is absent or activated. The statements carry no `ORDER BY`; the Rust store answers in slug byte order (`rust/crates/gbrain-store/src/generations/atom_reads.rs`), and the callers fold the rows into a set. Pinned by `test/engine-sql-caller-raw-sql-pins.test.ts` and `test/engine-parity/generation-output-parity.test.ts`.
- `src/core/engine-sql/derivation-trust.ts` + `src/core/rust-engine/store-members/derivation-trust.ts` + `rust/crates/gbrain-store/src/trust/derivation.rs` — the derived-row trust writes as engine members. `lowerTrustTier` lowers listed rows whose stored tier ranks above the target (`taint.ts` `lowerToDerivedTier`; the Rust member serves pages only). `countDerivedRowTaint` and `countDerivedFactTaint` count rows whose `write_origin` holds `taint_inputs` (doctor's derived taint share). `stampPageFrontmatter` merges one fixed stamp: `retired_by`/`retired_at` on soft-deleted pages (`derived-retirement-hold.ts`) or `source_hash` on live atom pages (the atoms adapter's `completeItems`). Each PGLite and Postgres text is the caller's text byte for byte (`test/engine-sql-caller-raw-sql-pins.test.ts`); `test/engine-parity/generation-write-parity.test.ts` walks a derivation publish, a retirement and an atoms publish on every engine (on Rust the two publishes still stop at the raw `derivation_inputs` write).
- `src/core/engine-sql/generation-page-rows.ts` — the page row read of `src/core/generations/adapters/page.ts` `readPageRows` as one engine member, `readGenerationPageRows`. Each `match` is one statement the page adapters sent: `slug` (the single-page adapter's row of its page), `synthesis` (the listed slugs and the live dream-generated pages of a transcript's locator), `atoms` (atom pages of the listed slugs, or live atoms whose `source_slug` or `source_path` is the origin) and `chronicle` (the listed slugs and the live Life Chronicle events of a depth). Every engine checks the query first, so an unknown match or atoms field refuses the same way. Rows come by slug, deleted rows included, with tags sorted and `segmented` set; a segmented row is held `segmented_unsupported`. PGLite and Postgres send the statements page.ts sent, with `COLLATE "C"` on the slug order and the tag order, so every engine and locale answers in byte order, as the Rust store does from its page records (`rust/crates/gbrain-store/src/generations/page_rows.rs`). Pinned by `test/engine-sql-caller-raw-sql-pins.test.ts`, `test/engine-parity/generation-output-parity.test.ts` and `test/engine-parity/generation-page-rows-order.test.ts` (fails without `COLLATE "C"` on an en_US Postgres).
- `src/core/engine-sql/chronicle-events.ts` + `src/core/rust-engine/store-members/chronicle-events.ts` — the statements of the Life Chronicle event adapter (`src/core/generations/adapters/chronicle-events.ts`), `src/core/chronicle/publish.ts` and `src/core/chronicle/event-identity.ts` as engine members: `readChronicleDepthRow`, `listChronicleOwnedHashes`, `listRetiredGenerationItemKeys`, `listEventProjectionRows`, `listPageContentHashes` (`ids` or `live_slugs`), `listLiveGenerationItems`, `hasChronicleSkipDecision`, `readEventProjectionId`, `pageSlugExists`, `deleteEventProjections`, `restoreEventProjection`, `listOrphanedChronicleOwners` and `listChronicleEventSlotRows`; the chronicle advisor's coverage-gap read is `listChronicleCoverageGapRows`, served from the store's pages and timeline rows, and `advisor/collect-chronicle.ts` lets a capability refusal of it surface. PGLite and Postgres send the statements the callers sent, byte for byte (pinned by `test/engine-sql-caller-raw-sql-pins.test.ts`); the adapter and event-identity.ts send no raw SQL, and publish.ts keeps two statements on the managed path. The Rust store serves them from its page, ledger and timeline records (`rust/crates/gbrain-store/src/generations/chronicle_events.rs`, `timeline_queries/event_rows.rs`; reference: `rust/docs/store/generations.md`); it has no chronicle ledger yet, so `listChronicleOwnedHashes` answers none and `hasChronicleSkipDecision` false. A real chronicle publication still stops on a Rust brain at the derivation edge write (`facts/derivation-inputs.ts`). Pinned by `test/engine-parity/chronicle-publish-parity.test.ts`.
- `src/core/engine-sql/generation-fence-restore.ts` — the reads of `src/core/generations/fence-restore.ts` (the fence restore of `gbrain repair generations`) as three engine members: `readGenerationFenceBlocks` (the recorded `completeness.fence` block of each generation), `listOwnedGenerationItems` (the item keys each generation owns, retired items left out) and `readLiveGenerationId` (the live row the apply rechecks). PGLite and Postgres send the statements fence-restore.ts always sent, ordered by id and item key in byte order; the Rust store answers from its ledger rows (`rust/crates/gbrain-store/src/generations/fence_restore.rs`). Pinned by `test/rust-generation-fence-restore.test.ts`.
- `src/core/engine-sql/fence-holds.ts` + `src/core/rust-engine/store-members/fence-holds.ts` — the fence generation statements of `src/core/generations/fence.ts` as engine members: `listFenceHoldRows`, the read of held facts and takes fence results (`derived_generations` rows in state `held`) behind `listFenceHolds`, which `get_page`, the doctor generations check and `gbrain sync status` list; `readFenceHoldFiles`, the held pages' file state behind `fenceHoldEntries`; `readFenceOriginGone`, the deleted-page recheck of a publish; `lockGenerationKey`, the generation key lock; and `clearFenceHoldRows`, the `fence_absent`/`no_proof` rows a readable fence clears. PGLite and Postgres send the statements fence.ts always sent, on the engine's own `executeRaw`. On Rust the generation key lock is the store's write: a transaction holds the store's writer gate from open to commit, so two writers of one key run one after the other (pinned by `test/rust-fence-generations.test.ts`, with the advisory lock on Postgres). On Rust the held read and the clear answer from the store's derived generation family; the page reads answer from its pages.
