- `src/core/write-gate-store.ts` + `src/core/write-gate-schema.ts` — `write_gate_receipts` (flag/quarantine verdicts per persisted target, unique on target, content hash and detector version; pattern names only) and `write_gate_holds` (quarantined facts/takes kept out of `facts`/`takes`; a hold remembers its page's permanent id in `page_id`, so renaming the page never lifts it, and has two disjoint dedupe keys: a bound hold is unique on source, page id, fingerprint and detector version, an unbound one (written before any page took its slug) on source, slug, fingerprint and detector version; a hold with `page_candidates` (an upgrade could not tie it to one page) has no key; re-arrival re-opens a decided hold and takes the new slug with the new payload). Writers record inside their publication transaction: `recordPageGateReceipt` resolves the live page row, `recordWriteGateReceipt`, `recordWriteGateHold` (takes the optional `pageId` a producer already read, else resolves the page at source and slug inside the same INSERT, so it takes no page lock; with no page the hold stays unbound); `decideFactWrite` / `decideTakeWrite` return insert/hold/reject per row and `recordFlaggedRow` receipts an inserted flagged row. Owner review: `listWriteGateHolds`, `getWriteGateHold`, `releaseWriteGateHold` (returns the payload for the confirm path; authorization is the caller's), `dropWriteGateHold`; `pruneWriteGateReceipts` drops receipts unseen for 365 days except a pending hold's. `write-gate-binding.ts` holds what readers and sweeps share: `holdAppliesToPageSql` (a hold applies to its bound page; an unbound hold applies to the page at its slug, to a candidate page, and to a page the same source's rename record, `slug_aliases` and `slug_rename_history` with chains followed, leads to from its slug, which covers a hold that committed after its page was first created), `holdOwnedByDeletedPageSql` (a purge deletes by page id, or an unbound hold with no candidate list whose slug is, or leads through the rename record to, the purged slug, and only while that record reaches no other surviving page; `dropPurgedCandidates` takes a purged page out of a candidate-marked hold's list and deletes the hold only when no candidate survives; `holdKeptForSurvivorSql` is the other half, the unbound candidate-free holds a purge names but keeps because another page row is still reachable, which the purge statements note through `noteKeptHoldsCte` into `write_gate_hold_rechecks` with `holdVersionSql` and the surviving page ids, in the delete decision's own statement and without locking the hold; a brain before v337 purges without noting) and `carryHoldsToPage` (the identity carry merges identical twins and keeps a differing one as a candidate-marked hold, never dropping it); `engine-sql/hold-binding.ts` binds the unbound holds waiting for a slug when a page is first created there, inside the page-insert transaction (a hold whose rename record already leads from the slug to another existing page stays unbound: the new page only reused the name); `trust/hold-page.ts` finds the page a release lands on (the bound page under its current name; a purged page or a candidate-marked hold is refused, and a journaled release refuses a candidate-marked hold at preparation and again under the final hold lock); migration v333 backfills by classification and doctor `write_gate_hold_ambiguous` (`doctor/checks/write-gate-hold-ambiguous.ts`) lists the still-held candidate-marked holds (first 50, read-only). `write-gate-recheck.ts` `sweepHoldRechecks` (run by `bookkeeping_gc`, migration v337 adds its notes table) checks the noted holds again: it reads at most 500 notes oldest first and consumes only those note ids; per hold, in its own transaction with `row_security = off` that locks only the hold row (`FOR UPDATE`, no page key: `gbrain trust release` locks the hold row first), it deletes the hold and its receipts only while the hold is unbound, has no candidate list, still has a noted version (a hold re-opened later stays), no page row, live or soft-deleted, is at a slug it reaches, and no noted surviving page id still exists; hold ids stay text. Known limits: a rename onto a name the hold reaches that commits during the check does not stop the delete (it removes stale over-hiding and shows no held text), and a consumed note's surviving page ids are gone, so on rename history that is not flat a later purge of that page can leave the hold, as before the sweep. It deletes nothing and reports `row_level_security` with the hidden relations when row security is active for the role on any evidence table, and reports `engine_capability_missing` on an engine without raw SQL. Tests: `test/write-gate-store.test.ts` (+ Postgres arm `test/e2e/write-gate-store-postgres.test.ts`), `test/hold-page-id.test.ts` (+ `-postgres`, `-migration`, `-lifecycle`), `test/write-gate-hold-recheck.test.ts`.

- `src/core/access/owner-only.ts` — owner-only sources: a source of a kind in `OWNER_ONLY_KINDS` (`imessage`) or with `owner_only: true` in `sources.config` is read only by the local CLI and by a credential bound to the brain owner speaking for itself (`CallerAccess.owner`). Decided at read time by `gbrain_owner_only_lineage` (v320; v322 adds the `owner_only_marks` a delete leaves, below). `ownerOnlyPageSql`, `ownerOnlyFactSql`, `ownerOnlyTakeSql` and `ownerOnlyTimelineSql` match a row in an owner-only source, a synthesized concept with a `concept-provenance` input there, a row whose `derivation_inputs` (followed transitively, with no depth limit and cycle-safe) reach a page, fact, take or timeline row there, or a marked row; each is guarded by the zero-argument `gbrain_owner_only_lineage()`, so a brain with no owner-only source and no mark never calls the row test. From v328 each read passes `gbrain_owner_only_read_mode()` (the `mode` form), which reads lineage closed for a login whose reads of the lineage tables or the marks are not complete; a page or fact whose source row the login cannot read counts as owner-only. Below v320, or when the schema version is unknown, the closed form (`ANY_OWNER_ONLY_SQL`, or the `OWNER_ONLY_HELD` flag on `owner_only_marks`) treats every row as owner-only on a brain that holds or has held owner-only data. `src/core/search/private-visibility.ts` appends them to the mandatory member-access part of the page and fact policies (no grant, hatch or lineage switch relaxes them), and `src/core/persistence/page-visibility.ts` refuses a remote write into an owner-only source from any credential but the owner's (`page_not_found`). `ownerOnlySourcesPresent` and `sourceIsOwnerOnly` fail closed. Tests: `test/imessage-owner-only.test.ts` (every caller class under each relaxation), `test/owner-only-read-side.test.ts`, `test/e2e/owner-only-marks-scoped-login.test.ts`, `test/e2e/imessage-source-postgres.test.ts`. `ownerOnlySourcesPresent` and `sourceIsOwnerOnly` read through the typed engine members `readOwnerOnlySourcesPresent` and `readOwnerOnlySourceConfig` (SQL in `engine-sql/sources.ts`; a Rust brain tests its source rows with `isOwnerOnlySourceConfig`), or run the same statement over an executeRaw-only view; an unreadable answer still counts as owner-only.
- `src/core/access/owner-only-marks.ts` + `src/core/engine-sql/owner-only-marks.ts` + `src/core/schema-migrations/v322-owner-only-marks.ts` — GST-3032: owner-only lineage outlives its origin. A `BEFORE DELETE` trigger on `sources`, `pages`, `facts`, `takes` and `timeline_entries` records the deleted row and every row derived from it in `owner_only_marks`, which `gbrain_owner_only_lineage` reads; nothing derived is deleted. The triggers run as the deleting role (no SECURITY DEFINER, #7659): a role whose reads row-level security limits gets `owner_only_lineage_unreadable` deleting a row it sees as owner-only, and its delete of a row it sees as open sets the `('*', 'row_security')` mark. The guard reads `OWNER_ONLY_HELD`, a one-way comment on `owner_only_marks` set by the first owner-only source or mark, so a brain that never held owner-only data never reads the marks; the table has row-level security and no policy, a login that cannot read every mark reads lineage closed, and its deletes on a held brain are refused with `owner_only_marks_unwritable`. `ensureOwnerOnlyMarkTriggersAtRun` creates each trigger every migration run where the role owns the table and names the rest on stderr; while one is missing on a brain holding owner-only data, the `('*', 'unguarded')` mark makes lineage read closed until the owner deletes it. `BrainEngine.ownerOnlyMarkTriggers` is the shared state read; doctor `owner_only_marks_triggers` (`src/commands/doctor/checks/owner-only-marks-triggers.ts`) names a missing or disabled trigger with its owner fix, each login that still needs the marks grant (with the GRANT and CREATE POLICY statements), and the row-security mark. Operator docs: [ENGINES.md](../../ENGINES.md#owner-only-delete-triggers). Tests: `test/owner-only-removal-lineage.test.ts`, `test/engine-parity/owner-only-marks.test.ts`, `test/e2e/owner-only-marks-scoped-login.test.ts`.
