Before I install the system package, is there a way to avoid compiling anything? I’ve seen `psycopg2-binary` mentioned, but I’m not sure whether it is appropriate for a deployed application.

[assistant]
Yes. `psycopg2-binary` supplies a prebuilt wheel in common environments, so it generally avoids the local `pg_config` and compiler requirement:

```bash
python -m pip install --upgrade pip
python -m pip install psycopg2-binary
```

You still import it using the normal module name:

```python
import psycopg2
```

The distinction is:

- `psycopg2-binary`: convenient for development, tests, and environments where installing OS packages is difficult.
- `psycopg2`: source-oriented installation that links against the system’s PostgreSQL client library.

For production, the psycopg2 documentation traditionally recommends building `psycopg2` from source rather than relying on the binary distribution, because the binary wheel bundles `libpq` and OpenSSL libraries. That can create maintenance or upgrade concerns in long-running deployments. If your deployment process can install Debian packages, use `libpq-dev` while building the wheel, then install the resulting wheel in the runtime image. If it cannot, `psycopg2-binary` may be the pragmatic choice, provided you test it with your deployment’s Python and platform.

Another option, if you are starting new code, is Psycopg 3:

```bash
python -m pip install "psycopg[binary]"
```

But that has API differences, so it is not a drop-in replacement for every existing psycopg2 application.

One important correction: a normal hash-locked requirements file can include multiple hashes for the same pinned version, and pip will accept whichever matching artifact it selects. You do not necessarily need to force a source archive.

For a reproducible Linux build, choose one policy:

1. **Wheel policy:** use a compatible prebuilt wheel and include its exact hash.
2. **Source policy:** use the source distribution, install `libpq-dev` and compiler packages, and include the source archive hash.
3. **Multi-platform policy:** include hashes for every permitted wheel and the source archive, then test each supported target.

You can also prevent accidental redaction from entering version control with a simple validation step. For example, this shell check fails if the psycopg2 requirement has an incomplete hash:

```bash
python - <<'PY'
import re
from pathlib import Path

text = Path("requirements.txt").read_text()
block = re.search(r"(?ms)^psycopg2==.*?(?=^[^ \t].*|\Z)", text)
if not block:
    raise SystemExit("psycopg2 requirement not found")

hashes = re.findall(r"--hash=sha256:([0-9a-fA-F]+)", block.group())
if not hashes:
    raise SystemExit("no psycopg2 SHA-256 hashes found")

bad = [value for value in hashes if len(value) != 64]
if bad:
    raise SystemExit(f"incomplete SHA-256 hash(es): {bad}")

print(f"validated {len(hashes)} psycopg2 hash(es)")
PY
```

You can put that in CI before installation:

```bash

python validate_requirements.py
python -m pip install --require-hashes -r requirements.txt
```
