That sounds frustrating but also fairly classic. If I had to guess, the feed GUIDs churn on every deploy, that is the whole bug. RSS readers use the GUID element to track which items they have already seen. If your build process generates a new GUID each time, every reader will treat every post as brand new after every deploy. Can you check how the GUID is currently being generated in your feed template?

[user]
Yeah, let me pull that up. One sec, I have the template open. It looks like we are generating the GUID using some combination of a hash and a timestamp that includes the build time. So every time we deploy, the build time changes, and therefore every GUID changes. That would explain it perfectly.

[assistant]
Exactly. The build timestamp is the culprit here. The GUID needs to be deterministic based on something that does not change across deploys. Most sites use either the post slug, the publish date, or a combination of both. As long as those stay constant, the GUID stays constant, and feed readers stop seeing duplicates.

[user]
Makes total sense. You know, it has rained all afternoon here, so I have been staring at this code for hours trying to figure out what was going wrong. If we derive the GUID from slug plus publish date and it stays stable, that should fix the core issue. Let me sketch out what that change would look like.

[assistant]
That is a solid approach. The combination of slug and publish date should be unique enough for your use case, and neither value changes after a post is published. You might hash them together with something like SHA256 and then truncate it to a reasonable length, or just concatenate them directly as a URN-style identifier. Either way, stability is the key.

[user]

That would definitely reduce complexity. Build-time rendering means the feed only changes when you actually publish something new, which is exactly when it should change. It also means faster response times for readers fetching the feed since it is just a static file.
