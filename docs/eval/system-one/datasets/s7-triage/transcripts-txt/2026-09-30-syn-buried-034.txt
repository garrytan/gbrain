The mirror now has the wheel, and the dry run works. I want to make the deployment reproducible and avoid accidentally getting a source archive later. Should I pin only `lxml==5.2.2`, or should I record a hash too?

[assistant]
For a controlled deployment, pin both the version and the expected wheel hash. A version pin prevents normal upgrades, while a hash pin prevents pip from accepting a different file for that requirement.

First download the exact artifact from the internal index:

```bash
rm -rf /tmp/lxml-wheel
mkdir -p /tmp/lxml-wheel

python -m pip download \
  --dest /tmp/lxml-wheel \
  --only-binary=:all: \
  --no-deps \
  --index-url https://packages.example.net/simple \
  lxml==5.2.2
```

Calculate its SHA-256:

```bash
sha256sum /tmp/lxml-wheel/lxml-5.2.2-cp312-cp312-manylinux_2_28_x86_64.whl
```

Then use a requirements entry like this, replacing the example digest with the output from your command:

```text
--only-binary=:all:
lxml==5.2.2 \
    --hash=sha256:REPLACE_WITH_ACTUAL_SHA256
```

Install with hash checking enabled:

```bash
python -m pip install \
  --require-hashes \
  --index-url https://packages.example.net/simple \
  -r requirements.txt
```

If your requirements file includes transitive dependencies, `--require-hashes` requires hashes for those too. Generate or maintain a fully pinned lock-style requirements file rather than adding a hash only for `lxml` if the whole deployment is meant to be reproducible. Keep `--only-binary=:all:` as an explicit guard against a source build.

One more concern: our build image is Ubuntu 22.04, but the runtime image is much smaller. How do I determine whether the `manylinux_2_28` wheel will run there, and when would compiling against the runtime’s system libraries be preferable?

[assistant]
Check the runtime image’s architecture and glibc version, then test the actual import in that image. The wheel’s `manylinux_2_28` tag indicates a glibc baseline, not that every Linux image is compatible. For a glibc-based runtime, run:

```bash
docker run --rm your-runtime-image sh -c '
  uname -m
  getconf GNU_LIBC_VERSION || true
  ldd --version 2>&1 | head -n 1 || true
'
```

You can inspect the wheel’s native libraries after downloading it:

```bash
unzip -q /tmp/lxml-wheel/lxml-5.2.2-*.whl -d /tmp/lxml-unpacked
find /tmp/lxml-unpacked -name '*.so*' -print
ldd /tmp/lxml-unpacked/lxml/etree*.so
```

The most reliable check is an isolated container test using the same runtime image:

```bash
docker run --rm \
  -v "$PWD:/app" \
  -w /app \
  your-runtime-image \
  python -c 'import lxml.etree as e; print(e.LXML_VERSION)'
```

If the runtime is Alpine Linux, it uses musl rather than glibc. A standard `manylinux` wheel generally will not be the right artifact; use an Alpine-compatible wheel if available, or build in an Alpine-compatible environment. Compiling against runtime libraries is preferable when the runtime is musl-based, when the runtime glibc is older than the wheel baseline, or when policy requires linking to approved system libraries. It also means you must install the compiler, Python headers, `libxml2-dev`, `libxslt1-dev`, and related packages in a builder stage, then copy only the resulting environment and required runtime libraries into the final image.
