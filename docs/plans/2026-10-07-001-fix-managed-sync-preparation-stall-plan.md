# Plan: managed sync never stalls on one stuck preparation (#6278)

Thread: GBRA-59. Issue: https://github.com/garrytan/gbrain/issues/6278 (filed by garrytan-agents, 2026-10-08 03:07Z, v0.60.105.0, managed Postgres via Supavisor).
Related: #6188 (fence holds and repair, shipped in waves 10–11), #5984 (catch-up throughput, GBRA-45, PR `capy/sync-feeder-fast-writes` merging next), #5406 (writes stuck queued), #6176 (claim phase stamps).

## The problem in one paragraph

A ~13.6k-entry managed catch-up (`gbrain sync --source default --no-pull --no-embed`) runs for 10–15 minutes, then one write sits in `running` / claim phase `preparing` for 700 s and growing. Its owner keeps renewing the 30 s claim lease every 10 s, so the lease never lapses, nothing behind it on the worktree root runs, and the non-TTY watchdog kills the process at 3600 s (`sync_deadline_stop`, rc 143). The next pass re-enters the same state. Four passes in a row, 153 of 13,627 entries in 3.3 h. The stall begins right after `[persistence] phase=preparation reason=invalid_params` lines from two fence errors (correlation, not proof). Separately, the global maintenance job's `fence_repair` and `chronicle` phases refuse with `owner_unavailable`, so the repair that should clear held fences never runs.

## What the code says today (read on master 7aa2caa0, v0.60.106.0)

1. **No preparation deadline for sync or maintenance writes.** `src/core/persistence/consumer.ts` `execute()` sets `bounded = row.operation === 'remember' || ((put_page|edit_page) && !row.intent?.kind)`. Only those get the 30 s `preparationMs` budget. A `managed_sync_import` member, a `managed_maintenance_*` request, and every other intent kind prepare with no deadline, while `startClaimLease` renews the claim every 10 s through `executeRawDirect` (the session-mode direct pool). The group path (`src/core/persistence/group-publish.ts` `executeClaimedGroup`) prepares four members at a time under one group lease and has no deadline at all. This is exactly the shape the reporter sees: `phase: preparing`, `resumes_on_its_own: false`, "its owner is still renewing the claim". (amended: CEO) Two corrections. Only the *single* path renews through `executeRawDirect` (`consumer.ts:545-548`); the group path renews with `renewGroupClaims`, which runs `engine.executeRaw` on the ordinary pool (`journal.ts:321-325`; GBRA-45 branch `journal.ts:343-347`). And the existing 30 s deadline does not race the preparation: the timer only calls `abort.abort()` (`consumer.ts:539-543`) while `await lease.whileHeld(preparation)` (`:552`) still waits on the promise itself, so the deadline works only because the put_page/edit_page preparers honour the signal. The service dispatcher passes no signal to sync or maintenance preparers (`service.ts:67-68`; `prepareManagedSyncMutation(engine,row,_config)` at `sync-prepare.ts:207`), the group path never passes one (`consumer.ts:615`), and a lost claim keeps the root blocked until the abandoned preparation settles (#5373, `consumer.ts:421-423,553-555`). `test/persistence-consumer-scheduling.test.ts:201-226` pins the current behaviour that a preparation ignoring its signal stays `running` past the deadline.
2. **The stuck preparation has no step name.** `#6176` stamps `claim_phase` (`preparing` | `publishing`) on every renewal (`src/core/persistence/claim-phase.ts`). Nothing records which step of `prepareManagedSyncMutation` (`src/core/persistence/sync-prepare.ts`: authority, worktree binding, git `rev-parse`, raw hash, origin checks, knowledge publication, import screen, link resolution) is in flight, or whether the step is waiting on a pooled connection, a Postgres lock, git, or the filesystem. `health.ts` therefore reports `cause_unknown` even though the phase is known. (amended: CEO) `syncGit` is a synchronous `execFileSync` with a 30 s timeout (`sync-discovery.ts:50-52`): it is bounded, and it blocks the event loop while it runs, so renewals that keep firing every 10 s prove the stuck await is asynchronous. Git `rev-parse` is effectively ruled out as the unbounded wait.
3. **Lease renewal and preparation use different pools.** Renewals go through `executeRawDirect` (direct session pool), preparation queries through the regular pool (`max` = `GBRAIN_POOL_SIZE`, default 10, postgres.js queues waiters forever). Up to `concurrency` single preparations, lane groups publishing in long transactions (GBRA-45: up to six groups at once), the projection worker and the effects worker all share those 10 connections. A JS-level wait inside a transaction for a second pooled connection, or plain saturation, starves preparation while renewals keep succeeding. This is the leading hypothesis for *why* the preparation never finishes; it is unproven and must be proven or eliminated in Phase 0. (amended: CEO) Saturation is already partly guarded: `pool-budget.ts:15-24` caps long holds at `max-1`, `pool-capacity.ts:9-25` caps publication concurrency, and `resolveLanes` clamps lanes to the long-hold capacity minus 3 (`sync-group.ts:48-61`; GBRA-45 `:62-71`), so six lanes is the ceiling for a pool of ten, not a default. If the blocker is a *group* member, its renewals succeed on the same ordinary pool that would be starving it, which argues against total starvation. `src/core/pool-gauge.ts:5-14` states there are no public checkout counters, so the pool cannot today tell a queued checkout from a server-side lock wait.
4. **Fence adoption writes are doomed before submission.** `src/core/facts/unfenced-facts.ts` `fenceManaged()` (called from the `extract_facts` cycle phase and the v0.32.2 migration) renders a facts fence and submits `managed_maintenance_adopt_fact_fence`. `prepareFactFenceAdoption` (`src/core/persistence/prepared-maintenance.ts:290`) re-parses the rendered fence and refuses with `invalid_params` "The adopted fence row does not render its legacy fact." when `cell.claim !== fact.value.fact` or visibility differs. That is an internal render→parse round-trip mismatch, not caller input. (amended: evidence, parent probe 2026-10-07) A `renderFactsTable` → `parseFactsFence` round trip over 24 claim shapes shows pipes, newlines, backslashes, backticks, 1200-char claims, unicode and emoji all round-trip; exactly four shapes do not: trailing whitespace (`"x "` → `"x"`), leading whitespace, whitespace-only (`"   "` → `""`) and CRLF (`"a\r\nb"` → `"a\nb"`). The parser trims cells and normalizes line endings, the renderer does not, and the check compares the parsed cell with the raw `facts.fact` column, so any legacy fact stored with surrounding whitespace or CRLF is refused on every replan. That matches the reporter's nine refusals per pass on the same pages. Nine such refusals per pass, each a terminal `failed` write that consumes a claim, logs a preparation failure and teaches nothing: no hold, no repair candidate. (amended: CEO) Correction: `failed_pages` does record the exception text (`unfenced-facts.ts:256-257`, surfaced as a warning by `cycle/extract-facts.ts:487-492`), but its advice ("report the request ID to the user") is not actionable. Both voices found more shapes the codec changes beyond the parent's four: a claim of the form `~~x~~` parses back *inactive*, a literal `<br>` parses back as a newline, a lone CR comes back as LF, and U+00A0 is stripped by JavaScript `trim` but not by Postgres `btrim` (codec in `fence-shared.ts:30-54,76-101`). `planFence` also matches existing fence rows on the raw claim (`unfenced-facts.ts:176-180`), and each terminal refusal mints a fresh attempt id on the next run (`prepared-maintenance.ts:262-266`), which is why the same pages refuse on every pass.
5. **A `repeated_marker` fence defect in a timeline section fails a sync member instead of holding it.** `compileCanonicalProjections` (`src/core/persistence/canonical-projections.ts:297`) throws the typed `invalid_fence` (wire `invalid_params`) for the first defect. ~~#6218~~ #6188 E10 (amended: CEO) made the sync hold such files (`src/core/persistence/sync-holds.ts`, `src/commands/sync/holds.ts`), but the reporter saw neither a hold nor a `fence_repair` candidate on 0.60.105. ~~The hold is written by the sync process when it consumes the failed receipt; if the stall (1) lands first and the watchdog kills the process, the receipt is never consumed, and the next pass re-admits and re-fails the same page.~~ (amended: CEO, refuted by both voices) A watchdog kill does not lose the hold: `convertBlockedCursor` re-holds the entry at the start of the next run (`sync-run.ts:396-421`). The real gap is that *both* hold paths, `convertBlockedCursor` (`sync-run.ts:404`) and `holdFailedFenceRequest` (`sync-run.ts:445-450`), refuse to write the hold while **any** request on the whole source is `queued`/`running`/`recovering`, and return `partial`/`writer_pending` instead. A stuck preparation (1), or the steady stream of `extract_facts` adoption writes on the same source, therefore blocks every fence hold indefinitely. GBRA-45 keeps the same source-wide wait (`sync-run.ts:417,448-469`). This links problems 1 and 2 of the report: the stall is what prevents the hold. Separately, the managed screen already holds residual fences *before* admission (~~`sync-screen.ts:85`~~ `sync-run.ts:317-321` with `sync-screen.ts:128-150`; `sync-screen.ts:85` is `prepareTimeFenceHold`, the hold built from a failed receipt; amended: DX), so a `repeated_marker` refusal at preparation means either stored-row-dependent fences (the `prepare_time` hold path) or a request that is not a sync member at all (an adoption or maintenance page write on a page whose stored body already has the defect); Phase 0.5 checks which. The sync hold work is #6188 (E10); the plan's "#6218" reference is unverified. `repeated_marker` is a `manual` tier reason (`src/core/fence-repair/reasons.ts:66`), so even a hold never self-repairs; the user is told to merge the two fences by hand.
6. **`fence_repair` refuses with `owner_unavailable` for a reason unrelated to the sync.** `src/core/fence-repair/repair-io.ts:85` sets `ownerElsewhere` when `binding.owner_host_id !== localHostId() || binding.state !== 'active' || !binding.local_path`. A running sync is reported as `sync_in_progress`, not `owner_unavailable`. `localHostId()` is a UUID in `<persistenceHome>/host.json`, so a maintenance worker launched with a different `GBRAIN_HOME`, user, or launchd environment than the sync CLI has a different host id and is "another host". ~~The binding can also sit in `recovering` after a SIGTERM mid-publication.~~ (amended: CEO, refuted) A worktree binding goes to `recovering` only during topology clone add/reclone (`topology-clone.ts:139-143`) and to `draining` only during writer transfer (`ownership.ts:273`); it is *request* rows that go to `recovering` after a kill (`journal.ts:630`). `maintenancePreflight` (`prepared-maintenance.ts:78-83`) refuses chronicle on a wider predicate than repair: missing binding, wrong source incarnation, missing coordination path, host mismatch, inactive state or missing local path. The function in `repair-io.ts` is `loadFenceSource`, not `sourceView`, and the owner check runs before the sync check (`repair/fences.ts:264-268`). `GBRAIN_HOME` resolves to `<GBRAIN_HOME>/.gbrain` (`config.ts:1865-1881`), so host.json lives at `<GBRAIN_HOME>/.gbrain/persistence/host.json` (`identity.ts:37,55-59`). The reporter's guess (sync holds the owner role) does not match the code; the cause is a host-id split, a wrong-incarnation or incomplete binding, or a genuinely different host, and Phase 0.1 decides which.

## Goals

- G1. A catch-up never stops making progress because of one request. Any single write that cannot finish preparing is taken off the root within a bounded time and the rest of the root keeps moving. (amended: CEO) Stated as an invariant, not a budget table: while the database and control path work, no unpublished request keeps root execution past a hard ceiling. Preparation is *cancelled* (the signal reaches every preparer and its queries), the consumer races the preparation against the deadline on both the single and the group path, and a late result can never publish (the execution-token fence). An abandoned await that ignores cancellation is never silent: it is stamped, the request is held, and if the #5373 root block would otherwise keep the root waiting on it, the mechanism Eng chooses (isolate the zombie, or exit the sync with a distinct exit code so the zombie dies with the process) still guarantees the next pass moves past the entry. (amended: DX/Eng: settled in 1.9 — barrier to the ceiling, then isolation with a per-process cap; a CLI owner ends the drain `resumable` and exits, a resident owner reports `restart_required`; no new exit number. The guarantee needs every owner process on the new version.)
- G2. `gbrain sources writer status --json` names what a stuck preparation is doing (step, and what it waits on), so the next report carries evidence instead of `cause_unknown`. (amended: CEO) The step is always named; the wait cause (`git`, `fs`, `db`, `pool`) is reported only when it is observed, otherwise `unknown`. A truthful `unknown` beats a confident wrong repair command, so "never reports `cause_unknown`" is not a release gate.
- G3. Fence problems never consume the write path: a fence that cannot be rendered or parsed becomes a hold with a reason and (where a tier applies) a `fence_repair` candidate, never a repeated terminal failure. (amended: CEO) The hold lands even while unrelated requests on the same source are still queued or running. For *maintenance* writes (fact-fence adoption, maintenance page writes) there is no manifest entry to hold: a row or page that cannot be written without a fence defect is not submitted at all, and is reported with its reason in `failed_pages` and in doctor's `fence_integrity` (and, for a fence defect already in the stored page, as a `fence_repair` candidate), so it never becomes a repeated terminal failure.
- G4. `fence_repair` and `chronicle` run on the owner host while a sync is running, or say precisely why they cannot, with the exact command to fix it. (amended: CEO, restores the user's direction) The target is that repair actually runs during the sync for every candidate whose path is neither in flight nor still ahead in the sync's frozen manifest; the precise refusal is the fallback for a genuinely different host, not an alternative outcome. For the reporter's case the acceptance check is "the three held candidates repaired", not "the refusal is clearer".
- G5. ~~The reporter's run (13.6k entries, Supavisor, `--no-embed`) drains in one pass at the GBRA-45 throughput (≥300 pages/min steady) with zero `sync_deadline_stop`.~~ (amended: CEO, the ≥300 figure has no source) The GBRA-45 bench measures 152.8 pages/min steady with six lanes at 57 ms (`docs/eval/managed-sync-catchup.md` on the GBRA-45 branch, "Parallel lanes" table), so 13.6k entries take about 90 minutes. ~~longer than the 3600 s non-TTY watchdog.~~ (amended: DX, refuted by both DX voices) The non-TTY deadline is progress-aware: it extends while pages commit and stops only after a stall window without progress (`sync-reconcile.ts:161-206`; live-sync.md), and the reporter's outer `timeout` was 14400 s. A healthy 90-minute catch-up can finish in one pass, so the one-pass goal stands. Goal: zero stalls caused by a single request; a stuck request costs at most its budget times the attempt limit; steady throughput within 20% of the bench on the same fixture and RTT; every pass checkpoints and the next pass resumes without re-stalling; (amended: DX) one pass drains the fixture, because budget × attempts (240 s) and the hard ceiling both stay inside the watchdog's no-progress window. The final report separates "processed every manifest entry" from "imported every page" (held, stale and missing counts), because holds deliberately leave content behind.
- G6. (added: CEO) A systemic fault is not reported as a pile of file holds. When many entries in one run hit the preparation deadline (the existing `GIT_HOLD_ESCALATE_*` thresholds, `sync-holds.ts:48-52`), the run stops with one systemic diagnostic naming the step and the evidence instead of holding every file and calling the pass complete.
