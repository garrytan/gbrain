### 1.1 stdio server (`src/mcp/server.ts`)

Lifecycle, in order (`startMcpServer`, lines 339-635):

1. `loadConfig()` (`:340`), `assertStdioSourceBindable(engine)` (`:345`, refuses a well-formed `GBRAIN_SOURCE` that no active source backs), surface resolution (`:357`, see 2.5).
2. Writeback resolution (`:374`, ambient writeback; opt-in, default off) and `stdioAmbientOpts` (`:375`).
3. `new Server({ name: 'gbrain', version: VERSION, description: MCP_SERVER_DESCRIPTION }, { capabilities: { tools: { listChanged: true }, resources: {} }, instructions })` (`:376-388`). Instructions are resolved at `initialize`, not construction, by `installInstructionsResolver` (`src/mcp/instructions.ts:229`, used at `server.ts:391-400`).
4. Capabilities resource and skill resources installed with `installCapabilitiesResource` (`src/mcp/capabilities.ts:34`) and `createSkillResources` (`server.ts:403-425`).
5. Handlers: `ListToolsRequestSchema` (`server.ts:443-447`), `CallToolRequestSchema` (`server.ts:460-527`). There is no `prompts/*` handler, no `logging/*`, no `completion/*`. Server capabilities advertised: `tools.listChanged = true`, `resources = {}`. No `prompts`.
6. `server.connect(transport)` (`:531`). Engine-dependent boot (resolve IPC, session GC, startup sweep) runs after the first `tools/list` or after `BOOT_LIST_GRACE_MS` (25 ms, `server.ts:53`), or after `BOOT_WITHOUT_INITIALIZE_MS` (1000 ms, `:54`), via `deferredBoot` (`server.ts:69-97`). Tool calls await the boot (`awaitCall`, `:82`).
7. Shutdown: stdin `end`/`close` (unless `MCP_STDIO=1`, `:626-629`), SIGTERM, SIGINT, SIGHUP (`:632-634`), transport close (`:631`). Shutdown cancels the sweep, closes IPC, shuts harvest and delegated sync, disconnects the engine, then `process.exit`. The in-flight RPC counter (`trackStdioRpc`, `server.ts:264-276`) lets EOF drain before exit (#4409).

Status-only (degraded) mode: `statusModeOf(engine)` (`server.ts:373`). `tools/list` returns only `[STATUS_TOOL_DEF]` (`:444`); `tools/call` for `gbrain_status` answers from the status payload, others get `statusModeErrorResult` until a recovery probe succeeds (`:463-469`).

Framing: `mcpStdioTransport` uses `StdioServerTransport` with `maxBufferSize: 64 MiB` (`src/mcp/stdio-lifecycle.ts:26-30`). The SDK default is 10 MiB.

`initialize` result (produced by the SDK `Server` plus the instructions resolver):

- `protocolVersion`: SDK-negotiated (`2025-11-25` is the SDK's latest; the Rust port needs to match the client's requested version against the supported list, see section 7).
- `serverInfo`: `{ name: "gbrain", version: "0.60.733.0", description: "<MCP_SERVER_DESCRIPTION>" }`. The description is 104 characters (`src/mcp/instructions.ts:31`: "Shared memory: search gbrain before external lookup; remember what the user explicitly asks you to keep.").
- `capabilities`: `{ tools: { listChanged: true }, resources: {} }`.
- `instructions`: the contract text, built per handshake from the caller's callable set (section 3.9 and Appendix A).

`tools/list` returns `{ tools: McpToolDef[] }` (`server.ts:443-447`). No pagination.

Notifications the server sends: `notifications/tools/list_changed` on `request_tools` widen (`server.ts:293-295`) and on degraded→recovered (`server.ts:587-589`). Resource changes are not notified.

Resources (stdio): `gbrain://capabilities` (`src/mcp/capabilities.ts:5`) plus the skill resources (`gbrain://skills...`, `src/mcp/skill-resources.ts:11`). `resources/read` for skills awaits the deferred boot (`server.ts:57-59`). Unknown URIs throw `McpError(InvalidParams, 'Unknown resource')` (`capabilities.ts:42`).

Per-request tool list (stdio): `stdioVisibleTools` (`server.ts:215-247`) re-reads publish gates on every `tools/list` (no caching, `:209-211`) and the writer grant scopes via `verifyLocalWriter`, then applies `isCallable(..., { transport: 'stdio', surface: 'full', scopes, publishGates })`. Stdio keeps `localOnly` ops (`:208`). Gate reads fail closed (`:238-240`).

Calls: `dispatchToolCall(engine, name, params, { remote: true, transport: 'stdio', inboundFrameBytes, takesHoldersAllowList: ['world'], sourceId, localFederatedSourceIds, explicitReadBinding, surfaceCeiling, stdioSurface, revealTools, isListed, allowedOps, surface, metaHook, ... })` (`server.ts:495-526`). Remote is `true`, so every stdio call is agent-facing, even though it is a local pipe. `ctx.remote === false` is only set by `handleToolCall` (`server.ts:644-670`, used by the CLI `gbrain call`).

`_meta.session_id` from the request is threaded as `sessionId` (`server.ts:484`). `_meta.brain_hot_memory` is injected from `getBrainHotMemoryMeta` (`server.ts:518`).

### 1.2 Thin-client stdio bridge (`src/mcp/remote-bridge.ts`)

A stdio MCP server with no engine. It relays every request to the remote OAuth brain using the install's stored credential (`cfg.remote_mcp`). It builds no `OperationContext` and runs no handler, so it cannot act as the trusted CLI (`remote-bridge.ts:1-15`).

- Client name sent to the host: `gbrain-stdio-bridge` (`remote-bridge.ts:39`).
- Per-call timeout: 180 s (`:41`), overridable with `--timeout`.
- Minimum host version for audience semantics: `0.60.543.0` (`:43`).
- `tools/list` is the host's own list for this client's token, narrowed (never widened) by `--surface` and `--advertise` (`remote-bridge.ts:177`, using `stdioToolListing`, `surface.ts:425`).
- `tools/call` returns the host's `CallToolResult` byte-identical, including `isError` envelopes and write receipts. Bridge-generated failures use v1 envelopes from `remote-bridge-errors.ts` (`bridgeCallFailure` `:148`, `bridgeRefusal` `:206`).
- Bridge log lines go to stderr with prefix `[gbrain-bridge]` (`remote-bridge-errors.ts:25`).
- Capabilities advertised: `tools: { listChanged: true }` (`remote-bridge.ts:158`); no resources.
- Retry constant `BRIDGE_RETRY = { tries: 3, delay_s: 2 }` (`remote-bridge-errors.ts:30`). The call sites were not traced in this pass.

The bridge uses `listRemoteToolDefs` and `forwardRemoteToolCall` from `src/core/mcp-client.ts` (imported at the top of `remote-bridge.ts`, used at `:99-103`). `src/core/mcp-client.ts` is outside the MCP directory and was not read in full.

### 1.4 Legacy bearer HTTP (`src/mcp/http-transport.ts`)

Standalone `Bun.serve` transport with the same tool surface logic but its own auth and protocol code.

- Endpoints: `GET /health` (unauthenticated, `:366`), `POST /mcp` (`:393-398`; other paths 404, other methods 405, both as JSON bodies).
- Auth: `Authorization: Bearer <token>`, SHA-256 match in `access_tokens` (`:291-343`); a token whose `member` binding is disabled is refused with `code: access_member_disabled` (`:312`, `:195-197`).
- Initialize: `protocolVersion: '2025-03-26'` hard-coded (`:474`), regardless of the client's requested version. Capabilities: `{ tools: {}, resources: {} }` (`:476`). `serverInfo` carries `name`, `version`, and `description` (`:475`).
- `notifications/initialized` returns 204 with no body (`:491-494`). Other notifications, including `ping`, return HTTP 400 with `{error: 'unknown_method'}` (`:598-602`), not a JSON-RPC error.
- Results are `{ result, jsonrpc, id }` on success and `{ jsonrpc, id, result: { isError: true, ... } }` for tool errors (`:550`). Protocol errors that are not tool errors are a non-JSON-RPC body.
- Body cap: 1 MiB default (`:69`, `GBRAIN_HTTP_MAX_BODY_BYTES`), 413 with `payload_too_large` plus a suggestion (`:71-74`, `:418-421`).

## 2. Auth and access rules

### 2.1 Two independent axes on every call

`OperationContext` (`src/core/ops/contract.ts:477`) carries two flags that the port must keep apart:

- `remote: boolean` (`contract.ts:502`). `false` only for the trusted local CLI (`gbrain call`, `handleToolCall` at `server.ts:644`). Every MCP transport sets `remote: true`. Scope enforcement, publish gates, bound-client fences and source fences all key off `remote`. Trust is only granted for `remote === false` (`contract.ts:499-500`).
- `transport: 'stdio' | 'http' | 'cli'` (`contract.ts:511-520`, `dispatch.ts:222`). This is the locality axis. `localOnly` ops dispatch only when `transport === 'stdio'` (`dispatch.ts:1251`), and `isCallable` denies `localOnly` unless the transport is stdio (`callable.ts:30`). `transport` never grants trust.

### 2.2 Scopes

Defined in `src/core/scope.ts`:

- `ALLOWED_SCOPES` (`:27-38`): `read`, `write`, `admin`, `sources_admin`, `users_admin`, `agent`, `skill_editor`, `skill_publisher`, `skills_member_self`, `memory_confirm`.
- Hierarchy (`IMPLIES`, `:162-173`):
  - `admin` implies `admin`, `sources_admin`, `users_admin`, `write`, `read`.
  - `write` implies `write`, `read`.
  - `read` implies `read`.
  - `sources_admin`, `users_admin`, `agent`, `skill_editor`, `skill_publisher`, `skills_member_self`, `memory_confirm` each imply only themselves.
- `hasScope(granted, required)` (`:186-193`) ignores unknown granted strings.
- `operationScopesAllowed(granted, op)` (`:195-200`): `hasScope(granted, op.scope ?? 'read')`, or `op.agentCallable === true` and `hasScope(granted, 'agent')`.
- Discovery `scopes_supported` (`scopesSupportedForDiscovery`, `:142-146`): with DCR on, `read write`; with DCR off, every scope except `agent` and `memory_confirm`.
- DCR ceiling (`DCR_REGISTRABLE_SCOPES`, `:65`): `read write`. Machine (`client_credentials` DCR) ceiling (`:72`): `read`.
- Local-CLI-only scope (`LOCAL_CLI_ONLY_SCOPES`, `:82`): `memory_confirm` may be granted only by the local CLI on the brain host. Admin HTTP API, admin SPA, DCR and grant profiles all refuse it (`:74-81`, `:85-90`).

HTTP per-call scope check (OAuth): `callMcpTool` denies with `denied_after_list` when `operationScopesAllowed` is false (`serve-http-mcp.ts:380-383`); cliOnly ops skip the scope check so the owner-only refusal shows instead (`:380`, #5575). The legacy transport performs the same check (`http-transport.ts:545`).

Stdio scope: stdio has no per-token scope. `dispatchResolvedCall` enforces `requiredScopes` (not `scope`) for stdio, using the local writer registration grant (`dispatch.ts:1374-1384`, `:1395-1412`). A `read`-scope op on stdio is always allowed; ops with `requiredScopes` need the local writer grant.

### 2.4 The one callability predicate (`src/core/ops/callable.ts`)

`isCallable(op, ctx)` (`:25-34`) is the predicate shared by `tools/list` and `dispatch`:

1. `ctx.allowedOps` (if set) must contain the name (`:26`).
2. `filterOpsForSurface([op], ctx.surface)` must be non-empty (`:27`).
3. `transport === 'cli'` → true (`:28`).
4. `op.cliOnly` → false (`:29`).
5. `op.localOnly` and transport is not stdio → false (`:30`).
6. `publishGateKey` must be true in `ctx.publishGates` (`:31`).
7. HTTP: `operationScopesAllowed(scopes, op)` (`:32`).
8. stdio: no `requiredScopes`, or `operationScopesAllowed` (`:33`).

`opAllowedForBoundClient(auth, op)` (`src/core/ops/context.ts:502-515`) is the second predicate and is applied on HTTP only (listing and dispatch). The third is the `attest` filter in `listMcpTools` (`serve-http-mcp.ts:313-317`). Publish gates are a fourth predicate on the list path only; their call-time check is in the handlers (section 2.3).

Pipelines:

- OAuth `tools/list` (`serve-http-mcp.ts:285-355`): `mcpOperations` (surface filter plus `allowedOperations` grant, `:207-208`) → `isCallable` (`:315-316`) → `opAllowedForBoundClient` (`:317`) → attest filter (`:313-317`) → `advertisedOps` (`:328`, `mcp.advertised_surface` narrowing; `request_tools` kept) → `buildToolDefs` with per-request `strictParams` (`:325-328`).
- Legacy `tools/list` (`http-transport.ts:514-537`): publish gates → `isCallable` → `opAllowedForBoundClient`. Scope is applied by `isCallable` via `scopes`.
- stdio `tools/list` (`server.ts:443-447`): `stdioVisibleTools` (`:215`) → `listing.listed` (`stdioToolListing`, `surface.ts:425`) → `buildToolDefs`.
- Dispatch (all transports): `dispatchResolvedCall` (`dispatch.ts:1204`), in order: `allowedOps` check (`:1230`), op lookup, `localOnly` backstop (`:1251`), `cliOnly` refusal (`:1255`), `--source-guard` (`:1262`), validation (`:1284-1293`), unknown-key check (`:1302-1325`), missing source scope (`:1335-1346`), `requiredScopes` (`:1374-1384`), bound-client fence (`:1389`), read trust floor (`:1391`), handler (`:1412`).

### 2.6 Read-only access

`--access read-only` on stdio only (`surface.ts:186-195`, refused for HTTP at `serve.ts:330`). The stdio surface is intersected with `isReadOnlyOperation(op)` = `scope === 'read' && mutating !== true && no requiredScopes` (`surface.ts:197-199`, `:500`). `allowedOps` is set to exactly the surfaced names (`:501`), so `request_tools` (mutating) cannot widen it (`surface.ts:177-181`). Owner maintenance (startup migrations, hook IPC banking) is a separate control (`:179-181`).

HTTP read-only is per token: `authInfo.allowedOperations` (grant, `serve-http-mcp.ts:208`) plus scopes. A `read` token sees 81 of the 179 non-localOnly ops with gates off (section 0.2).

### 2.7 Bound clients (slug fence and operation grant)

An OAuth client row carries the bound-client columns `bound_slug_prefixes`, `bound_max_concurrent`, `budget_usd_per_day`, `surface` and the grant list (persisted fields listed at `oauth-provider.ts:60-62`). The fence:

- `CLIENT_FENCED_WRITE_OPS` (`src/core/ops/context.ts:433-469`): the write ops that enforce the slug fence on submission (`put_page`, `delete_page`, `restore_page`, `add_tag`, `remove_tag`, `add_link`, `remove_link`, `add_timeline_entry`, `revert_version`, `edit_page`, `append_page`, `put_pages`, `begin_page_upload`, `upload_page_part`, `get_page_upload`, `commit_page_upload`, `abort_page_upload`, `put_raw_data`, `think`, `submit_agent`, `capture`, `get_write_request`, `list_write_requests`, `cancel_write_request`, `takes_add`, `takes_update`, `takes_resolve`, `takes_supersede`, `takes_remove`, `put_skill`, `delete_skill`, `remember`).
- `BOUND_CLIENT_META_OPS` (`:482`): `request_tools`, `join_brain`, `sync_brain_skills`, `leave_brain`. Allowed even when the fence is degraded.
- `opAllowedForBoundClient` (`:502-515`): `grantProjectionDegraded` denies; an `allowedOperations` list must name the op; reads are always allowed; a degraded fence denies every non-read op except the meta ops; a bound client may only use ops in `CLIENT_FENCED_WRITE_OPS`. Any non-read op outside that set (including `forget`, `forget_fact`, `sources_add`, `sources_remove`) is denied for a bound client.
- `enforceBoundClientOpAllowList` (`:559`) throws the `permission_denied` (`fence=operation_grant`) error for a denied op, with a `fix` naming `gbrain auth rescope-client --allowed-operations ...`.
- `NO_SOURCES` (`permissions.source_id: []`): every op is refused with `fence=no_source_grant` (`:522-532`, `:563`).

### 2.8 Source scoping

Stdio source (`resolveMcpStdioSourceScope`, `server.ts:99-158`): resolved through the same chain as the CLI (`GBRAIN_SOURCE`, then `.gbrain-source`, then tiers). Non-explicit tiers may widen to `localFederatedSourceIds`; explicit, env and dotfile scopes stay scalar. A malformed env value is never treated as a binding (`:145-156`). In degraded mode the function never touches the engine (`:120-126`).

OAuth source (`serve-http-mcp.ts:428-443`, `:474-476`): `authInfo.sourceId` (from `oauth_clients.source_id`, backfilled to `default` by migration v60). `localFederatedSourceIds` from `noGrantFederatedScope` only when the credential has no operator source grant (`hasSourceGrant === false`, legacy tokens only).

Read scoping (`sourceScopeOpts`, `src/core/ops/context.ts:646-665`): if `auth.allowedSources` is a non-empty list → `sourceIds` (federated read). An empty list is not "all sources" (`:650-652`). The `__all__` sentinel spans the brain only for `remote === false` (`:654-658`). A remote `__all__` matches no source and reads empty. An explicit `NO_SOURCES` throws `noSourceGrantError` (`:647`).

Missing source scope: a remote call with no `sourceId` is refused with `missing_source_scope` (`dispatch.ts:1335-1346`), so the `default` fallback is never used for remote callers.

Private pages: `privatePagesAuth(grant)` (`grants/model.ts`) sets the granted private sources; `dispatchToolCall` passes `privateSources` only for reads (`dispatch.ts:1027`), except `context_pack` and `delta` which stay world-only unless a trusted local caller passes `include_private` (`:1018`, `WORLD_ONLY_PACK_OPS` `:999`).

`takesHoldersAllowList`: stdio and the legacy token path default to `['world']` (`server.ts:501`, `serve-http-mcp.ts:420-421`). Takes by private holders stay hidden on remote paths.

### 2.9 Subagent fences

The minion subagent tool registry uses `BRAIN_TOOL_ALLOWLIST` (`src/core/minions/tools/brain-tool-allowlist.ts:17`), a reviewed list of read ops plus a few writes. The MCP `starter` surface imports it, never copies names (`surface.ts:41`, `:75-80`). Adding an op to the allowlist grants every subagent that op. `capture` is a direct literal in `STARTER_OPS` so subagents do not gain it (`surface.ts:98-103`).

## 3. Wire shapes

### 3.1 `tools/list` entry

Built by `buildToolDefs` (`src/mcp/tool-defs.ts:114-137`), one entry per op, in manifest order (section 7 risk R6):

```
{ name, description, inputSchema: { type: "object", properties: {...}, required: [...], additionalProperties?: false }, annotations? }
```

- `description` is the op's `description` string verbatim.
- `inputSchema.properties` = `paramDefToSchema(p)` per param, in `op.params` insertion order. Each fragment's key order is `type`, `description`, `enum`, `default`, `items`, `properties` / `required` / `additionalProperties` (`tool-defs.ts:44-57`). Key order is pinned for byte-stability (comment at `:40-42`).
- `type` for array params is `array`; `items` recurses through `paramDefToSchema`.
- Object params with `properties` emit a closed object (`additionalProperties: false`) with their own `required` (`tool-defs.ts:51-55`). Nested member `required` is an array even when empty.
- `required` = params with `required: true`, in declaration order (`tool-defs.ts:129-131`).
- `additionalProperties: false` appears on the top-level schema only when `mcp.strict_params = reject` (`tool-defs.ts:132`). With strict, `_meta` (object), `dry_run` (boolean) and `room` (array of string) are added to `properties` unless the op already declares them (`tool-defs.ts:68-85`).
- Not emitted: `$schema`, `title`, `minimum`, `minItems`, `exclusiveMinimum` (these are ParamDef fields the manifest carries, but `paramDefToSchema` does not copy them; `GST-927` comment at `contract.ts:267-277`).
- `annotations` are emitted only when set: the op's curated `annotations`, else `{ readOnlyHint: true }` for `mutating: false`, `{ readOnlyHint: false }` for `mutating: true`, plus `idempotentHint: true` when the write is idempotent (`tool-defs.ts:97-102`). 17 ops carry curated `annotations`; 16 of them set a `title` (e.g. `"recall (memory read)"`, `"memory_write (QM memory write)"`). `destructiveHint: true` is curated on `forget` only.
- No `outputSchema` is declared on any tool, so clients get no output validation contract. `structuredContent` is not promised by `tools/list`.

### 3.2 `tools/call` success

Built by `toolResultWithNotices` (`src/core/agent-output.ts:897-904`) and `assembleToolResult` (`src/mcp/dispatch.ts:1187-1202`):

- `content[0]` is `{ type: "text", text: JSON.stringify(result) }`. The text is the handler's return value as compact JSON (no indentation). Array results are arrays; the verbs return objects with `protocol_version` (section 6).
- Additional text blocks follow `content[0]` in this order: retrieval evidence blocks (`dispatch.ts:1193`, from `retrievalNoticeBlocks`), then one `noticeBlock` per rendered notice (`agent-output.ts:901`). Notice blocks are model-visible; the notice's rendered text starts with `[gbrain notice <code> kind=<kind>]` per the agent contract (`instructions.ts` item 4).
- `_meta` (optional) carries, per key, one producer each (`dispatch.ts:1196-1200`; `docs/protocol/MCP_META_CHANNELS.md`):
  - `gbrain_notices`: rendered notices (only when notices exist, `agent-output.ts:902`).
  - `access`: `{ member, groups, audience, policy_rev, relaxation, ... }` on every remote call (`dispatch.ts:1096`, shown in every probe below). `requester_scope` is added when a requester-scope notice applies (`:1098-1099`).
  - `warnings`: unknown-key warnings in warn mode (`dispatch.ts:1362-1364`).
  - `retrieval`, `room`: handler-emitted (`ctx.emitResponseMeta`).
  - `brain_hot_memory` and other hook keys: merged from `metaHook` (`dispatch.ts:1200`).
- `structuredContent` appears only on the QM memory tools and their refusals (`qmMemoryToolResult`, `src/core/ops/qm-memory.ts:487-501`): `memory_recall`, `memory_write`, `memory_propose`, and the personal tools (`QM_PERSONAL_OPS`, `:36`). For those, the JSON text object's `text` field becomes `content[0].text`, and the rest moves to `structuredContent` (`:496-500`). Results that are arrays become `structuredContent: { results: [...] }` (`:497`).
- `isError` is absent on success.

### 3.3 Tool error envelope (`isError: true`)

Built by `errorResult` (`dispatch.ts:883-897`) → `toAgentError` (`src/core/agent-output.ts:826`) → `toolErrorResult` (`agent-output.ts:907-909`):

- Exactly one `content` block, `{ type: "text", text: JSON.stringify(envelope, null, 2) }` (2-space indent), plus `isError: true`.
- Envelope fields (`AgentEnvelope`, `agent-output.ts:99-120`):
  - `error` (string): the frozen legacy value (e.g. `invalid_params`, `permission_denied`, `unknown_operation`). For some sites `error` differs from `code` (see below).
  - `code` (string): canonical registry code (`OperationError.canonicalCode`, `contract.ts:133-135`).
  - `message` (string): never echoes the caller's raw value (`validate-params.ts:43-46`).
  - `suggestion` (string): always populated (problem, cause, fix).
  - `docs` (string): `https://github.com/garrytan/gbrain/blob/master/docs/guides/error-codes.md#<code>` (from the probe below).
  - `docs_cmd` (string[]): `["gbrain","errors","<code>"]`.
  - `class` (string): `caller`, `host_only`, `server`, `unavailable`, etc. (classification in `agent-output.ts`).
  - `retryable` (bool): forced `false` for mutating non-idempotent ops unless the failure proves non-admission (`agent-output.ts:845`, `provesNotAdmitted`).
  - `contract_version`: `1` (`agent-output.ts:112`).
  - Optional: `reason`, `why`, `fix` (`RenderedAction`: `argv` or `mcp: {tool, arguments}`, `consent`, `actor`, `next`, `why`, `requires_exclusive`, `inputs`), `notices`, `detail`, `protocol_version` (verbs only), `write_request`, `write_error`, `request_id`, `fence`, `fence_issues`, `withdrawn`, `writable_source_ids`.
- Over HTTP, the envelope passes `redactForTransport(env, 'http')` (`agent-output.ts:850`).

### 3.5 Parameter validation order

Dispatch calls, in order (`dispatch.ts:1284-1325`; logic in `src/mcp/validate-params.ts`):

1. `normalizeOptionalParams(op, params)` (`validate-params.ts:141-155`). Drops absent optional values: `null` (any type), `""` on a string param, `0` below a `minimum` or `exclusiveMinimum` that excludes 0, `[]` where `minItems >= 1`, `{}` on a read where the object has a required member, `false` on an `actsWhenTrue` flag. Drops `appliesWith` params whose partner is absent. Copy-on-write. Required params are never normalised away.
2. `findInvalidParam(op, params)` (`:28-53`): required missing or `null` (`Missing required parameter: <name>`), then type checks in declaration order (`string`, `number`, `integer` → `Number.isInteger`, `boolean`, `object` non-array, `array`), then enum membership for strings. The first failure wins.
3. `findUnknownParams` (`:225-237`) against the normalised object. `_meta` and `dry_run` are allowed (`UNKNOWN_PARAM_ALLOWLIST`, `:186`). Suggestions come from edit distance over declared params (`suggestNearest`), plus aliases (`PARAM_ALIAS_HINTS` `:193-196`, `SOURCE_PARAM_ALIASES` `:199`).

Observed consequence (probe, `wire-examples.json`): the required check runs before the unknown-key check. `get_page {"slugg":"a"}` returns `Missing required parameter: slug` with no did-you-mean. Clients that typo a required name get the missing-param message; the typo is not named.

The error text for enums lists the declared values only (`Parameter "match" must be one of: hybrid, keyword`); the caller's value is never echoed (`validate-params.ts:43-49`).

`schemaInvalidParams` adds a `fix` only for read ops (`retryWithValidParam`, `validate-params.ts:86-108`): the same call with the enum's default or first value. Writes never get a fix (`:87`).

### 3.6 Redaction and logging

Three distinct redactions:

1. Response scanning (`outputRedaction`, `contract.ts:820-824`). Applied by the registration wrap in `operations.ts` to the whole response of every op whose policy is `retrieval`, including early returns (the wrap is referenced at `contract.ts:811-813`). `{ retrieval: { localVerbatim: [...] } }` leaves named keys unscanned for `remote === false` only. `{ exempt: reason }` returns stored text raw. `no_stored_text` promises no page, chunk, fact, take or transcript text. Manifest counts (204): `no_stored_text` 112, `retrieval` 53, `retrieval` with `localVerbatim` 3, `exempt` 36. The wrap's implementation (`redactRetrievalOutput`) is in `src/core/` and was not read in full; see section 7.
2. Request-log summaries (`summarizeMcpParams`, `src/mcp/dispatch.ts:403`; `serve-http-mcp.ts:399-405`). Logs declared keys only, no values, no attacker-controlled key names, unless `--log-full-params`. `session_key` is always replaced with `[redacted]` (`serve-http-mcp.ts:401`). The raw unknown key names must never reach `mcp_request_log` (`validate-params.ts:218-223`).
3. Error text in logs: `error_message` is the envelope `message` only (`serve-http-mcp.ts:635`).

The OAuth path logs one row per JSON-RPC method to `mcp_request_log` with `token_name`, `agent_name`, `operation`, `latency_ms`, `status`, `error_message`, `params` (JSONB) and broadcasts the same event on the admin SSE feed (`serve-http-mcp.ts:338-353`). Status values: `success`, `success_with_warnings`, `accepted_pending`, `denied_after_list`, `error`, plus `rate_limited`, `auth_failed`, `body_too_large`, `parse_error`, `unknown_method` on the legacy path (`http-transport.ts:405-598`).

## 4. Tool table

### 4.1 How to read the table

- One row per op that is not `cliOnly` (186 rows, sorted by tool name). `#` is the op's position in `OPERATION_MANIFEST` (the tools/list order before filtering; section 7 R6).
- **CLI**: `cliHints.name` from the manifest (`gbrain <name>`); `(hidden)` means `cliHints.hidden`. `—` means the op has no CLI name.
- **Surf**: `V` = verbs surface (`verb: true`), `S` = starter surface (`STARTER_OPS`), `F` = full surface (every op that is not cliOnly). F includes the 10 localOnly ops (stdio only; HTTP never lists them).
- **Scope**: the op's `scope`. `+x/y` is `requiredScopes`. `(+agent)` is `agentCallable`.
- **Mut**: `R` read, `W` write; `i` = `idempotent`.
- **Transport / gate**: `stdio-only` (localOnly), `gate <key>` (publish gate), `needs` (requiredScopes), `agent-callable`, `verb`.
- **Input params**: `name:type`; `*` required; `{a|b}` enum; `array<T>` items; `‡` absent on the starter surface (`fullSurfaceOnly` or `STARTER_HIDDEN_PARAMS`). Full JSON schemas are in section 5.
- **Output**: a heuristic. For verbs it is the `RESPONSE_SCHEMAS` property list (`verbs.ts:604`, the frozen fields). For the rest it is the top-level keys of the first object literal the handler returns (source scan, so helper-returned shapes can be wrong). Treat it as a pointer and verify in the handler before porting. `see handler` means no object literal was found.
- **Engine methods**: `engine.*` calls reachable from the op definition by following helper calls up to two levels (same file or an imported module). `(helper/SQL; see src)` means the op reaches no `engine.*` method through that scan.
- Handler files are in the `src` column of the generation script output; the full manifest with descriptions is `docs/research/rust-engine/data/operation-manifest.json`.

## 5. JSON input schemas (verbs surface and starter surface)

Format: JSON Lines, one `tools/list` entry per line (`name`, `description`, `inputSchema`, optional `annotations`), exactly as `buildToolDefs` emits it with `strictParams` off. Source: `docs/research/rust-engine/data/tools-list-verbs.json` and `tools-list-starter.json`, both verified JSON-equal to a fresh `buildToolDefs` run (section 0.3). The strict variant (`additionalProperties: false`, plus `_meta`, `dry_run`, `room` passthrough properties) is generated by `buildToolDefs(..., { strictParams: true })` and is not reproduced here.

The starter surface drops `‡` params (the verbs schemas keep them, so a verb's starter schema can be narrower than its verbs-surface schema). The verbs surface is the 7 frozen verbs only.

## 6. MEMORY_VERBS protocol and the qm-memory-provider contract

### 6.1 MEMORY_VERBS v1 (frozen protocol)

Document: `docs/protocol/MEMORY_VERBS_v1.md`. Code: `src/core/verbs.ts`, `src/core/ops/qm-memory.ts`.

What v1 freezes (`MEMORY_VERBS_v1.md:26-45`):

- Every field name and its semantics in v1, forever. Never removed, renamed, re-typed; meanings never change.
- New optional params and new optional response fields may be added at any time. A conformant client ignores unknown fields; a conformant server never rejects unknown-to-v1 additions it ships.
- `protocol_version` (integer, starts at `1`) rides every verb response and every verb error. It increments only on a breaking change, which requires a new `MEMORY_VERBS_v2` document (expected never). Code: `MEMORY_VERBS_VERSION = 1` at `src/core/verbs.ts:35`.
- Adding a verb is additive (`context_pack` and `delta` sit at `protocol_version: 1`).
- Enum values are part of the contract; enum derivation may improve without a bump.

## 7. Contract risks and open questions for the Rust port

### 7.1 Risks (things a port can get wrong without a compile error)

| # | Risk | Why it matters | Evidence |
|---|---|---|---|
| R1 | Protocol version handling differs by transport | stdio and OAuth use the SDK's negotiation: echo the client's version if the SDK supports it, else the SDK's latest. The legacy transport always answers `2025-03-26`. A Rust port must pick one rule for the OAuth/stdio transports and test both. | SDK `_oninitialize`: `node_modules/@modelcontextprotocol/sdk/dist/esm/server/index.js:259-263`; legacy `http-transport.ts:474` |
| R2 | SDK-level JSON-RPC validation is not reproduced here | The SDK parses every request with Zod-based schemas (`types.js`). Extra fields and missing fields are handled by those schemas, not by gbrain. Known case: `serve-http-oauth.ts:147-150` says the `/register` body schema strips unknown members, which is why the `token_ttl_seconds` hook reads the raw body first. The exact error codes for malformed `tools/call` or `resources/read` requests are not verified in this pass. | `serve-http-oauth.ts:147-158`; section 1.5 |
| R3 | Tool and schema bytes | Descriptions are TS string literals; some carry Unicode (for example the em dash in the `synthesize` annotation title). `JSON.stringify` writes non-ASCII raw and escapes only quotes, backslash, and control characters. The Rust port must emit the same UTF-8 and the same key order (R5). The verbs and starter JSON in section 5 are the oracle. | `tool-defs.ts:44-57`; section 5 |
| R4 | Schema draft | No `$schema` is emitted. Fragments use `type`, `description`, `enum`, `default`, `items`, `properties`, `required`, and `additionalProperties` (strict only). Clients infer Draft 7 or 2020-12. Do not add `format`, `minimum`, `minItems`, or `$schema` to match a different draft; those ParamDef fields stay server-side (`contract.ts:267-277`). | `tool-defs.ts:44-57`, `:132` |
| R5 | Key order | Object key order is observable in `tools/list` bytes. Order: `name`, `description`, `inputSchema`, `annotations` (per tool); `type`, `properties`, `required`, `additionalProperties` (per schema); param fragments in the order listed in 3.1. | R6 | Tool order | `tools/list` order is the order of the `operations` array after filtering. `OPERATION_MANIFEST` has the same order (the `#` column in section 4). | R7 | Dynamic instructions | `initialize.instructions` is computed from the caller's callable set, readiness, writeback, and deployment identity. Only the static text (Appendix A) is fixed. | R8 | Error results are tool results, not JSON-RPC errors | Almost every refusal is `result: { content, isError: true }`. A port that returns JSON-RPC `error` for these breaks clients that read `isError` and `content[0].text`. The thin-client bridge relays these results byte-identical, so the bytes matter. | section 3.3; `remote-bridge.ts:1-15` |
| R9 | Success text is compact JSON; errors are indented | `JSON.stringify(result)` vs `JSON.stringify(envelope, null, 2)`. Notice blocks are separate `content` entries. | `agent-output.ts:898`, `:907-909` |
| R10 | `_meta` key set and producer rules | Several producers, each per key. `access` is on every remote call (including errors). `_meta.gbrain_notices` is only on success with notices. | `dispatch.ts:1096`, `:1196-1200`; `agent-output.ts:902` |
| R11 | Redaction must match | `redactRetrievalOutput` (`src/core/search/output-redaction.ts:42`) is applied at operation registration to every `retrieval` op (53 ops) and to `localVerbatim` ops (3). Its scanner was not read in full in this pass; a port must reproduce the scan, or the response text differs for pages that contain secret-like strings. `redactForTransport` (`agent-output.ts:353`) applies to HTTP error envelopes. | `contract.ts:811-824`; manifest counts section 3.6 |
| R12 | Stateless HTTP | No `Mcp-Session-Id` is issued, so a Rust server must not require one. `GET /mcp` returns 405 with `Allow: POST, DELETE`, but no DELETE route is registered, so a DELETE falls through to Express's default 404. Decide whether to match that quirk. | `serve-http-mcp.ts:150-153`, `:722` |
| R13 | Legacy transport shape differs | `unknown_method` as HTTP 400 with a non-JSON-RPC body; initialize ignores the client's version; `notifications/initialized` returns 204. Only tests use it (section 1.4). | `http-transport.ts:474`, `:491-494`, `:598-602` |
| R14 | Stdio framing | Newline-delimited JSON; 64 MiB max per message on stdio (`stdio-lifecycle.ts:26`). Oversize closes the session (SDK behavior). | `stdio-lifecycle.ts:21-26` |
| R15 | Config dual plane | `mcp.*` values resolve DB first (`engine.getConfig`), then the file config, then the default. Read failures use the last-known-good DB value for `strict_params`, and hide gated ops for publish gates. Each request re-reads (OAuth, stdio `tools/list`), except stdio `strict_params` and `result_rows`, which resolve once at boot. | `publish-gates.ts:39-61`; `validate-params.ts:307-322`; `server.ts:430-434` |
