# BrainEngine map

This map lists every member of the `BrainEngine` interface in gbrain (TypeScript), grouped by family. For each member it gives the signature, what it does, the SQL it runs, where `PGLiteEngine` and `PostgresEngine` differ, and the tests that cover it.

- Reference: `garrytan/gbrain` at commit `8bbfd0b5e8` (master, 2026-11-16). Every `path:line` citation is relative to the gbrain repo root at that commit.
- Interface: `src/core/engine.ts:830-2890`. Engines: `src/core/pglite-engine.ts` (3,088 lines), `src/core/postgres-engine.ts` (3,182 lines), plus `src/core/pglite-engine/*` and `src/core/postgres-engine/*`. Shared SQL: `src/core/engine-sql/*.ts` (about 15,000 lines with the engines).
- Method: each family was read by a separate research pass. Counts are per declaration. Line numbers were read at the commit above. Test coverage was found by grep, not by running the suite. Items a pass could not verify say so in place.

Confirmed build direction: the first build target is a Rust storage engine that implements `BrainEngine` as a third engine inside gbrain, next to PGLite and Postgres (option B, confirmed by Garry). The binding is still open; a napi-rs native module is the leading option. The last two sections of this map serve that target:

- [What a Rust engine must do to pass engine-parity](#what-a-rust-engine-must-do-to-pass-engine-parity) has the per-method parity notes for `test/e2e/engine-parity.test.ts`.
- [Adding a third engine and binding options](#adding-a-third-engine-and-binding-options) covers engine selection and napi-rs vs sidecar vs WASM vs `bun:ffi` for Bun.

## Headline findings

- The SQL is mostly shared. Migrated storage domains keep their SQL once in `src/core/engine-sql/` and both engines delegate to it. Engine differences are in the wrappers: Postgres adds statement timeouts, JIT-off reads, reserved connections, read-only transactions, real cancellation and an exact-scan vector fallback. PGLite adds planner-stat refreshes and a single-process lock.
- Some engine differences are visible to callers. `searchKeywordChunks` ignores `type`, `types`, `where` and `exclude_slugs` on PGLite. The `stale` flag on keyword results is computed on PGLite and a constant `false` on Postgres. A Rust engine has to pick one behavior per method; the Postgres behavior is the safer reference.
- Several interface doc comments disagree with the code (`addLinksBatch`, `getEffectiveDates`, `createVersion`, `setPageAliases`, `updatePageContextualRetrievalState`, `insertFacts`). A Rust engine should follow the code and fix the doc first.
- `test/e2e/engine-parity.test.ts` covers only 60 of 197 members and needs `DATABASE_URL`. 46 of its calls are raw Postgres SQL through `executeRaw`. A Rust engine cannot pass it unchanged; see the parity section.

### Parity risks noted

- Keyword timeouts, JIT and work_mem: Postgres bounds keyword, title, count and CJK reads with `statement_timeout` (default 8000 ms, configurable 1-60 s), JIT off and `work_mem 32MB`. PGLite has none of these, so a slow query can run unbounded there. A Rust engine needs an explicit per-query deadline or it will not match Postgres behavior.
- Keyword candidate bound: Postgres caps keyword candidates at 50,000 chunks (`KEYWORD_RANK_CANDIDATES`). PGLite does not, so PGLite can rank more candidates and return different top-N under load.
- `stale` flag: PGLite computes per row `stale` from `timeline_entries`. Postgres `searchKeyword` returns `false AS stale` (postgres-engine.ts:1217), and `searchTitles` on Postgres disables the stale probe (`staleProbe: false`). Consumers see different `stale` values per engine.
- Vector search: Postgres has an exact-scan fallback and iterative HNSW scan (pgvector 0.8+), with an index-walk path and per-attempt budgets. PGLite has no exact fallback and no pool escalation beyond its own attempts (pglite-engine.ts:1733 comment). Result sets can differ when the ANN pool is short.
- Planner stats: PGLite runs `beforePlannerRead` (ANALYZE settle) around reads (`planner-stats.ts:389-420`). No planner-stats call was found in the Postgres engine file. Plan shapes differ, which can change ties in `ORDER BY score`.
- Transactions: Postgres honors `readOnly` (BEGIN READ ONLY), `pipelineEarly`/`pipelineFirst`, signal abort and commit checks. PGLite honors only `signal`. A read-only transaction on PGLite can write.
- `withReservedConnection`: PGLite ignores `route` and `selfContained`, has no `transaction` member, and does not enforce pool permits. Postgres enforces `PoolCapacityError` and direct-pool routing.
- `reconnect`: PGLite in-memory is a deliberate no-op (state preserved). File-backed PGLite does a full disconnect and reconnect. Postgres rebuilds pools with build-then-swap. Callers that rely on "reconnect restores the same state" behave differently in-memory vs file-backed PGLite.
- Schema lock: Postgres uses cross-process advisory key 42 (session or transaction form). PGLite serializes in-process only (`schema-migration-lock.ts:22-30`). PGLite `initSchema` also skips `verifySchema` and the zombie-index sweep that Postgres runs after migrations.
- Soft delete asymmetry: `softDeletePage` has no `'default'` source fallback. If `sourceId` is omitted, it can flip the same slug in every source (`pages.ts:276-295`), while `deletePage` defaults to `'default'`. `deletePages`, `softDeletePages` and `resolveSlugsByPaths` require `sourceId`.
- `getAllSlugs` includes soft-deleted pages (no `deleted_at` predicate, pages.ts:563-572). Its JSDoc says "every page in the brain", so callers doing existence checks can see tombstones.
- Unscoped reads on Postgres: `resolveSlugs`, `resolveSlugsByPaths`, `listAllPageRefs`, `listAllSources`, `getEmbeddingsByChunkIds` run on the pool without an RLS scope transaction (LegacyUnscopedRead brand). The Rust rewrite has no RLS, so these become plain reads, but any access control must be enforced in the app layer.
- Blank-body guard: `putPage` refuses to overwrite a non-empty or segmented body with a blank one unless `allowEmptyOverwrite` (pages.ts:116-133). Both engines share this logic, but PGLite's `reread` callback differs from Postgres's `RETURNING` assumption, and the Rust port must keep the same guard.
- Batch limits: `deletePages`, `softDeletePages`, `resolveSlugsByPaths` throw above `DELETE_BATCH_SIZE` = 500 (engine-constants.ts:25). Callers must chunk; a Rust port must keep the cap or the contract changes.
- Bind-parameter ceiling: PGLite batches under 30,000 bind params (`PGLITE_CAPABILITIES`, dialect-pglite.ts:25-29). Postgres is unbounded. Batched writes must stay under the PGLite ceiling if both engines stay in use during migration.
- Statement cancellation: PGLite cannot cancel a running statement (WASM). The abort race in `pgliteQuery` only settles the caller, the statement finishes in the background (dialect-pglite.ts:42-56). Postgres sends a real cancel. Timeout behavior differs under contention.
- Lock timeouts: Postgres schema replay runs under `lock_timeout` (schema-lock-timeout.ts) and `retrySchemaReplayOnDeadlock`. PGLite has no equivalent.
- Vector column binding: `getEmbeddingsByChunkIds` validates the column name by regex and quotes it. The Rust port must keep the same allowlist, since column names are interpolated.
- `listPrefixSampledPages` representative chunk uses `embedding IS NOT NULL` (hardcoded column) even though `getEmbeddingsByChunkIds` takes a column. Keep both behaviors aligned.
- Sampling determinism: `listCorpusSample` with `seed` depends on `setseed` followed by `ORDER BY RANDOM()` on the same connection (Postgres forces a transaction). PGLite is single-connection, so it matches, but the Rust engine must reproduce the same seeded order or accept a different sample.

## Chunks, Extraction staleness and Links/Graph

Scope: `BrainEngine` interface declarations in `src/core/engine.ts` lines 1240-1841 (the `// Chunks`, extraction-freshness and `// Links` blocks, ending before `// Tags` at line 1842). That range declares 45 methods: 15 chunk/embedding, 7 extraction staleness, 6 link writes, 17 link/graph reads. None of them is marked optional (`?`) in the interface.

Engine implementations compared: `src/core/pglite-engine.ts` (PGLiteEngine, 1812-2078) and `src/core/postgres-engine.ts` (PostgresEngine, 1626-1899). SQL lives in `src/core/engine-sql/chunks.ts`, `pages.ts`, `links.ts`, and in `src/core/search/read-enrichment.ts` (the graph and boost readers both engines share, via `executeRaw`), plus `src/core/derived-links.ts`.

Engine difference, in short: the SQL text is shared. The two engines differ in the read transaction wrapper and the planner/JIT handling around it:
- PGLite calls `scopedRead(this.engineSql)` directly, with no transaction. Several reads are wrapped in `plannerRead(...)` (`pglite-engine.ts:1992, 2015, 2029, 2077`), which can run `ANALYZE`-style planner refreshes (`src/core/planner-stats.ts:389-410`). Postgres never calls `plannerRead`.
- PostgresEngine wraps scoped reads in `withScopedReadTransaction(sourceIds, sourceId, tx => ...)` (`postgres-engine.ts:368`), which sets the source/RLS scope in a transaction. It also threads `chunkManifestReads` into chunk reads (`postgres-engine.ts:1642, 1650, 1658, 1856`). `chunkManifestReads` returns `true` on every non-Postgres engine (`src/core/search/safe-chunks.ts:107-113`), so PGLite omitting the argument is equivalent by construction.
- `getBacklinkCounts` on Postgres runs in `jitOffRead` (`postgres-engine.ts:1863-1867`, `prepare: true`). PGLite runs it through `executeRaw` (`pglite-engine.ts:2043`).
- The `unscopedExecutor(..., 'EO4 inventory')` wrapper marks reads that are deliberately unscoped on the master path. PGLite and Postgres both use it for `findByTitleFuzzy`, `traverseGraph`, `traversePathsDetailed`, `findOrphanPages`, `sumStaleChunkChars`, `getPageTimestamps`, and the `links`/`pages` reads that take no scope.

### B. Extraction staleness (engine.ts 1424-1482)

The predicate is `stalePagesWhere` in `engine-sql/pages.ts` (line 827). A page is stale when `deleted_at IS NULL`, not quarantined, and `links_extracted_at IS NULL` OR `links_extracted_at < versionTs` OR `updated_at > links_extracted_at` OR a wanted-producer origin is stale. Options: `attendance` ('exclude' | 'blocked', by `links_attendance_blocked_revision` vs `knowledge_revision`), `held` ('exclude' | 'only', `linkExtractionHeld`), and a guest-source exclusion. This is the shared watermark behind `gbrain extract --stale` and the `links_extraction_lag` doctor check.

### Parity risks noted

1. Planner wrapper asymmetry. PGLite wraps `getBacklinks`, `traverseGraph`, `traversePathsDetailed`, `traversePaths`' inner call and `findOrphanPages` in `plannerRead` (`pglite-engine.ts:1992, 2015, 2029, 2077`), which can run planner-stat refreshes. Postgres does not. A Rust engine has no equivalent, so timing and plan behavior differ and nothing in the tests pins it.
2. Transaction and RLS scope asymmetry. Postgres wraps scoped reads in `withScopedReadTransaction` (`postgres-engine.ts:368`), which sets the source/RLS scope. PGLite runs the same SQL on the bare connection. The source-scope predicates are in SQL in both, so behavior matches, but a Rust engine must enforce the same scope in its own read path.
3. JIT off on Postgres only. `getBacklinkCounts` runs in `jitOffRead` on Postgres (`postgres-engine.ts:1863`). PGLite has no JIT, so this is a performance-only divergence, but the inline comment says plan compilation dominated at 50k pages.
4. Generic-plan sensitivity. `getAdjacencyBoosts` and `relationalChainHop` inline integer id arrays and use `OFFSET 0` fences, to keep the planner from choosing a generic plan (`search/read-enrichment.ts:117-130, 265-288`). A Rust engine has no plan cache, so these are not needed, but the output ordering they rely on must hold.
5. Traversal caps. `TRAVERSE_WALK_ROW_CAP` = 20000 and `TRAVERSE_PATH_ROW_CAP` = 5000 (`engine-constants.ts:37, 48`) bound the walk, and `traversePathsDetailed` reports `truncated`. The cap counts raw rows before dedup, so a Rust version must apply the cap at the same point or the `truncated` flag changes.
6. Traversal ordering. `traversePaths` orders by `depth, from_slug, to_slug, from_source_id, to_source_id`. `traverseGraph` orders by `depth, slug, source_id`. `relationalFanout` orders by `hop ASC, edge_count DESC, source_id, slug`. Ties and collation (`ORDER BY slug`) must match on both engines.
7. Stale `addLinksBatch` JSDoc. `engine.ts:1507-1511` says "INSERT...SELECT FROM (VALUES)". The implementation is `jsonb_to_recordset` (`links.ts:216-227`, #1861). The doc is wrong and should not be copied.
8. `getEffectiveDates` JSDoc contradicts itself. `engine.ts:1788-1790` says "Returns NULL for refs with no row; map omits them." The implementation omits them (`read-enrichment.ts:311-320`). Callers must treat a missing key as absent.
9. Stacked JSDoc on `findOrphanPages`. `engine.ts:1802-1829` has two JSDoc blocks in sequence; the `mode` semantics (#4524) sit above a separate block. The `excludePrivate` option is accepted by both implementations but missing from the interface type (`engine.ts:1830-1834`).
10. Unscoped master reads. `sumStaleChunkChars`, `findByTitleFuzzy`, `traverseGraph`, `traversePathsDetailed`, `findOrphanPages`, `getPageTimestamps` use `unscopedExecutor(..., 'EO4 inventory')` on both engines. Their scope comes from the caller's options, not the engine. Any Rust read path that enforces scope centrally would change these results.
11. Segmented-body chunk visibility. `getChunks`, `getChunkPage`, `getChunkWindows`, `countStaleChunks`, `listStaleChunks` and `relationalFanout` all gate on `chunkGenerationFilter` / `chunkGenerationProbe` (`search/safe-chunks.ts:77-89`). It reads `page_body_manifest` (the segmented-body manifest), and the flag `chunkManifest` only changes behavior on Postgres (`safe-chunks.ts:107-113`). Rust must replicate the manifest semantics exactly, or segmented pages will read differently.
12. Content-drift sweep has no saved cursor. `invalidateContentDriftEmbeddings` loops in 5000-row transactions with no saved cursor (`chunks.ts:612, 685-698`). A crash mid-loop re-examines rows, which is safe by design (the predicate is idempotent) but the batch boundary is observable in the returned count.
13. Upsert is retried as a whole. `upsertChunks` and `addLinksBatch` are wrapped in `batchRetry` (`pglite-engine.ts:1814-1815, 1950`; `postgres-engine.ts:1628-1629, 1770`). The engine doc says "callers MUST NOT wrap externally." A Rust engine that retries differently changes the commit-ambiguous replay story (`engine.ts:1248-1253, 1512-1520`).
14. Embedding column routing. Every chunk read and stale count resolves the active column by a registry lookup (`resolveActiveEmbeddingColumnFromEngine`, `search/embedding-column.ts:694`), and the write path resolves it again from config rows inside the upsert. A fallback to the legacy `embedding` column on a broken registry (`fallbackToLegacy: true`) is a silent behavior change for diagnostics and reads.
15. Halfvec and dimension casts. `upsertChunks` writes `::halfvec(N)` or `::vector` depending on the resolved column (`search/embedding-column.ts:279-283`). A Rust store must keep the same dimension and type rules, or writes to a registry-routed brain fail with dimension mismatch errors.

### Parity risks noted

1. Clock sources differ. Reads and sweeps compare against the DB clock (`now()`, `current_date`), e.g. `getDreamVerdict`, `sweepDreamVerdicts`, `getContradictionCacheEntry`, `sweepContradictionCache`, `getOnThisDay`, `getLastSeen`, `getOntology` default `asof`. Some writes and computations use the JS clock: `putContradictionCacheEntry` expiry (`takes.ts:262-263`), `loadContradictionsTrend` cutoff (`takes.ts:195`), and `finalizeLastSeen`'s `days_ago` (`last-seen.ts:11-21`). Clock skew between app and DB changes results. A Rust rewrite has to choose one clock and keep both sides on it.
2. Transaction-local trust GUC. `ONTOLOGY_SUPERSEDE_GUARD` (`chronicle/ontology.ts:65`) reads `current_setting('gbrain.write_trust_tier', true)` in the same transaction. Ontology supersession depends on that session setting, not on a parameter. An embedded store needs an equivalent per-transaction writer tier.
3. Postgres-specific SQL features with no direct equivalent: `DISTINCT ON`, `json_agg`/`json_build_object`, `jsonb_to_recordset` (batch writes), `jsonb_array_elements_text`, `unnest(int[])`, `ON CONFLICT ... WHERE <partial index>` (`timeline_event_dedup`, facts dedup), `RETURNING (xmax = 0) AS created` (upsertFile created flag), `md5()` as a dedup key (timeline `md5(summary)`), `FOR KEY SHARE` (addTimelineEntry), `LATERAL ... OFFSET 0` planner fence (getTimeline), `make_interval`, `date_trunc('week')`, `EXTRACT(MONTH/DAY)`, `pg_trgm` `<%` and `word_similarity`, `pgvector` `<=>` and `vector_dims`.
4. Calibration bucketing relies on NUMERIC arithmetic (`takes.ts:661-665`). Float math would put boundary weights in a different bucket. The Postgres driver also needs explicit `::float` casts on bound scalars (`takes.ts:644-648`), so scalars are text-bound there. Rust must do exact decimal bucketing.
5. `files` identity mismatch. The DDL is `UNIQUE(storage_path)` (`schema.sql:1149`), while `getFile` and the file comment at `engine-sql/files.ts:41` describe identity as `(source_id, storage_path)`. The `ON CONFLICT (storage_path) DO UPDATE` never updates `source_id`. A second source writing the same storage_path keeps the first source's row, and `getFile(secondSource, path)` returns null.
6. `supersedeTake` allocates `row_num` as `MAX(row_num)+1` without a row lock (`takes.ts:554`). Two concurrent supersedes on one page can compute the same next row number. A Rust rewrite should allocate with a lock or sequence.
7. `addTakesBatch` ON CONFLICT is DO UPDATE (`takes.ts:62-63`). An intra-batch duplicate `(page_id,row_num)` fails the whole statement, and the claim-change reset of embeddings (`takes.ts:81-84`) must be reproduced exactly.
8. `updateTakeEmbeddings` silently drops a vector when the claim changed in flight (`WHERE t.claim = v.claim`, `takes.ts:502`). It returns the updated count only, so the caller cannot tell a dropped vector from a successful one.
9. `listStaleTakes` has a hard `LIMIT 100000` (`takes.ts:453`). Excess rows are dropped with no signal.
10. `loadContradictionsTrend` has no LIMIT (`takes.ts:196-205`). Result size is unbounded.
11. `searchTakesVector` has no dimension check in SQL (`takes.ts:385-401`). Mixed-width vectors fail in pgvector. The Rust version must decide what to do with mixed widths.
12. `getLastSeen` matches wikilinks with `LIKE ... ESCAPE '\\'` on `who` strings (`timeline.ts:243-245`). The escape rule has to be reproduced exactly, or wikilink matches will differ.
13. Reads on master are `LegacyUnscopedRead` (`engine-sql/brands.ts:33`): no RLS scope transaction. Any Rust rewrite that adds scope enforcement will change behavior in this range. The brands doc calls widening a TODO, not a drive-by (`brands.ts:17-21`).
14. Dialect cancellation differs. PGLite cannot cancel a running statement; `pgliteQuery` races a late abort (`dialect-pglite.ts:42-56`). Postgres uses real cancellation. Batch-write abort behavior is not identical.
15. Lock capability differs. `transactionAdvisoryLocks` is `false` on PGLite (`dialect-pglite.ts:27`) and `true` on Postgres (`dialect-postgres.ts:55`). `mutatePageTag` calls `lockPageKeys` on both. I did not trace the lock mechanism itself.
16. Type-only drift: PGLite's `searchTakes`/`searchTakesVector` opts type (`pglite-engine.ts:2648-2658`) omits `sourceId`/`sourceIds`. Runtime behavior is unchanged.
17. `resolveTake` and `updateTake` have no transaction and do a SELECT then an UPDATE (`takes.ts:571-576`). Concurrent resolves can race the immutability check. The engine's error code is the only guard.
18. `putRawData` without `sourceId` matches every same-slug page (`postgres-engine.ts:2101`, `pglite-engine.ts:2284`). Multi-source brains can get a 21000 error. The sourceId path avoids this.

### Parity risks noted

1. `searchKeywordChunks` filter drift: Postgres honors `type`, `types`, `where` (frontmatter filter) and `exclude_slugs`; PGLite (`pglite-engine.ts:1638-1724`) ignores all four. The `stale` flag also differs (PG constant `false` at `postgres-engine.ts:1398`; PGLite computed from `timeline_entries` at `pglite-engine.ts:1713`). Any caller that narrows anchors by type gets different results per engine. Rust needs one filter contract tested on both.
2. Fact insert concurrency: the per-entity advisory lock (`facts.ts:120-123`, `149-152`) exists only on Postgres. PGLite inserts do not serialize the dedup window; a Rust embedded engine that is single-writer is fine, but the dedup contract must not rely on the lock.
3. `createVersion` default source: when `sourceId` is omitted, `createPageVersion` uses `'default'` (`pglite-engine.ts:2710`, `postgres-engine.ts:2566`). The interface doc (`engine.ts:2459-2463`) says the bare-slug lookup picks whichever row Postgres returns first. The code does not do that. Rust should follow the code, or the doc should be fixed first.
4. `insertFacts` return alignment: `ids` drops ON CONFLICT-skipped rows (`facts.ts:318`), so callers cannot map index to id, contrary to the doc at `engine.ts:2236`. Keep the contract explicit (return `null` per input, or document the filter).
5. Embedding cast: Postgres probes `facts.embedding` for `::halfvec` vs `::vector` (`postgres-engine.ts:2271-2304`); PGLite always casts `::vector`. A Rust store with one fixed vector type must not depend on the probe; the dimension and type must be identical to what both engines read back.
6. `getEdgesByChunk` has two implementations (`pglite-engine/code-edges.ts` and `engine-sql/code-edges.ts:141-172`). The `engine-sql` header (`code-edges.ts:6-10`) still says PGLite runs "one UNION with a shared LIMIT", but the PGLite file now applies a per-table LIMIT. Comment and code have drifted; the Rust version needs one behavior.
7. `executeRaw` semantics: PGLite ignores `timeoutMs`, `deadlineAt`, `jitOff`, `prepare` and cannot cancel a running statement. Postgres cancels with `CancelRequest` and bounds with `statement_timeout`. Callers that rely on a timeout (search, Minion locks) see no bound on PGLite. The interface doc (`engine.ts:2696-2713`) describes Postgres behavior.
8. `setPageAliases` replaces only `origin = 'frontmatter'` rows (`pages.ts:1188`). The interface doc (`engine.ts:2572-2579`) says it deletes "the page's existing page_aliases rows". Declared and subject aliases survive a frontmatter rewrite on purpose; the doc is out of date.
9. `updatePageContextualRetrievalState` mode `'none'` also clears chunk vectors and `embedding_signature` when the old mode was `title` or `per_chunk_synopsis` (`pages.ts:431-...`). The interface doc (`engine.ts:2612-2628`) says it stamps only the two columns plus `updated_at`. A Rust port that follows the doc would keep stale vectors.
10. Segmented flip and staging: `flipBodyGeneration` relies on `FOR UPDATE` on the page row and staging row (`page-body.ts:294`, `309`), and `stageSegmentChunks` on advisory lock plus `FOR KEY SHARE` (`page-body.ts:193-197`, Postgres only). PGLite has neither. A Rust embedded store needs its own serialization (a per-page mutex or single writer) and must reproduce the generation checks (`revision_changed`, `body_staging_expired`, `generation_incomplete`).
11. `upsertSegmentDerivations` is not atomic across batches: earlier batches commit before `DerivationWriteRefused` is thrown (`page-body.ts:521-542`). `sweepSegments` runs six statements without one transaction (`page-body.ts:425-487`); its correctness depends on the ordering and grace windows (1 h texts, 1 h idle and 24 h hard staging deadlines, `page-body/limits.ts:132-135`).
12. Chunk indexes: `stageSegmentChunks` derives `chunk_index` from `MAX(chunk_index) + 1` per page and never reuses an index (`page-body.ts:219-221`). Deleted chunks leave gaps, so a Rust store must not compact indexes.
13. `runMigration` runs raw SQL text: PGLite `db.exec` vs PG `sql.unsafe` (`pglite-engine.ts:2908`, `postgres-engine.ts:2824`). Multi-statement and transaction-control behavior of migration files must be checked on the Rust side. The `version` argument is ignored.
14. `getStats` and `getHealth` run their own statements on each engine (`getStats` is inline in both; `getHealth` shares `health.ts` but is wrapped differently: PG `jitOffRead` per statement, PGLite `plannerRead`). Results must match across engines; the planner-robustness notes at `health.ts:20-27` mean a Rust rewrite cannot rely on query plans for correctness.
15. `resolveAliases` throws on pre-v110 brains (`engine.ts:2563-2566`), while `resolveSlugWithAliasDetailed` returns null on pre-v105 brains (`pages.ts:1194-1223`). Callers depend on these two different fail modes.
16. Config: Postgres retries connection-class failures on every config accessor (`postgres-engine.ts:2753-2765`); PGLite has no equivalent. The request-scoped config snapshot (`config-snapshot.ts`) is used by both, so reads can be served from a snapshot taken before a write in the same request.
17. Facts health and recall reads use `now()` for validity (`valid_until > now()`) in SQL on both engines, so results depend on the wall clock at read time (TTL honesty, `facts.ts:419-427`). A Rust engine has to evaluate the same predicate at read time, not at write time.

## What a Rust engine must do to pass engine-parity

Scope: `test/e2e/engine-parity.test.ts` (2762 lines, commit 8bbfd0b5e8), its helpers, and `docs/TESTING.md`. The file compares the Postgres engine against the in-process PGLite engine. No engine list is parametrized. A Rust engine has to be added by hand to every describe block. Five things block a pass as the file stands:

1. The file is gated by `DATABASE_URL`. Without it, 16 of its 17 describe blocks skip, including the PGLite half. Only the `getRawData` block runs (1 test).
2. About 46 `executeRaw` calls and 17 `installFixtureChunks` calls rely on Postgres SQL and on the page-projection protocol. A Rust engine must either run that SQL or the test must be rewritten to typed methods.
3. Test 1592 reads `EXPLAIN (FORMAT JSON)` plans and asserts index names. This is Postgres-only.
4. The file never compares scores (no `toBeCloseTo`). Ordering and exact nullability are what matter.
5. `undefined` vs `null` matters in several places (see section 4).

Counts: 17 `describe` blocks (16 `describeBoth` + 1 ungated `describe`). 74 static `test(` calls. The `for (const q of QUERIES)` loop at line 137 turns one `test` into 3 runs. With `DATABASE_URL` set, 76 tests run. Without it, 1 runs.

### 1. How the parity test is structured

**Gating.** `SKIP_PG = !hasDatabase()` and `describeBoth = SKIP_PG ? describe.skip : describe` (`test/e2e/engine-parity.test.ts:32-33`). `hasDatabase()` is `!!process.env.DATABASE_URL` (`test/e2e/helpers.ts`, `hasDatabase`). The header comment at lines 4-14 says "Always runs the PGLite half". That is wrong: the whole block is inside `describeBoth`, so PGLite is skipped too. The only always-on block is the `getRawData` describe at lines 2714-2762. Its arms array (`arms`, 2716-2723) pushes `pglite` always and `postgres` only when `!SKIP_PG`. That array is the closest existing pattern for a multi-engine list.

**Engine construction.** Postgres arm: `setupDB()` or `setupLegacyEmbeddingDB()` from `test/e2e/helpers.ts`. Both go through `db.ts` and `PostgresEngine`. `setupDB` TRUNCATEs every table in `ALL_TABLES` and re-seeds config (`test/e2e/helpers.ts`, `setupDB`). `setupLegacyEmbeddingDB` also configures the gateway to `LEGACY_EMBEDDING_CONFIG` (`test/helpers/legacy-embedding-config.ts`: `openai:text-embedding-3-large`, 1536 dims) and alters the vector column widths. Isolated variant: `isolatedPersistencePostgres()` in `test/helpers/persistence-postgres.ts` creates a fresh database per describe (used at 2386-2404 for open_loops only).

PGLite arm: `new PGLiteEngine(); await e.connect({}); await e.initSchema();` (for example 126-128, 1368-1370, 1457-1459). Each describe creates both and seeds them with the same function, usually `seedX(eng)` run twice.

Teardown: `afterAll` calls `pgliteEngine.disconnect()` and `teardownDB()` (30s timeout). beforeAll budgets are 90s, or 180s for the dense-hub block (2201).

**Fixtures.**
- Main corpus: `SEED_PAGES` (49-89) with 6 pages, each with `embeddingDim` and a one-hot embedding from `basisEmbedding(idx, 1536)` (35-39, `Float32Array` of length 1536).
- `QUERIES` (112-116): `'fat code thin harness'`, `'fat code thin harness part 3'`, `'fat code production'`.
- `seedEngine` (91-110): `putPage` + `installFixtureChunks` for each page, one `compiled_truth` chunk with `token_count = body.split(/\s+/).length`.
- Other seeds: `seedRelational` (1338-1359), `seedFederated` (1428-1447), `seedTraversal` (2023-2039), `seedDenseHub` (`test/helpers/dense-hub.ts`, 200 inbound + 200 outbound spokes, ring offsets, 5200 edges), `seedAliasOwners` (2241-2256), `seedKeyset` (1624-1639), CJK corpus (1952-1969), `seed` in the timeline plan block (1561-1568).
- Helper `installFixtureChunks` (`test/helpers/page-projection.ts`) calls `readProjectionSnapshot`, then `installPageProjection(..., {seal: true})`. These are in `src/core/page-state/projections.ts`. They use `engine.transaction`, `engine.lockPageKeys`, `engine.readPageSnapshot`, `engine.executeRaw("UPDATE pages SET text_projection_revision=knowledge_revision, search_vector=...")`, and `page_projection_jobs`. So a Rust engine must implement the projection revision model for the fixture helper to work at all.

**Comparison style.**
- Most tests run the same call on both engines and `expect(pgX).toEqual(pgliteX)`, or compare `new Set(...)`, or compare a derived shape string.
- Exact expectations are then pinned against absolute values, so both engines cannot be wrong in the same way.
- Ordering: `toEqual` on arrays is order-sensitive. Many tests `.sort()` first, which means they do not check order (see table).
- Scores: the only score asserted is `DreamVerdict.score` exact `0.31` (line 417). Search scores are never compared.
- Timestamps: checked with `instanceof Date`, `Number.isFinite(getTime())`, `toMatch(/\.\d{6}Z$/)`, or exact ISO strings (for example `'2026-09-01T23:59:59.000Z'` at 2477).

**Plugging in a third engine.** Concrete steps, based on the current code:
1. Extend the engine kind union: `readonly kind: 'postgres' | 'pglite'` (`src/core/engine.ts:832`), `EngineConfig.engine?: 'postgres' | 'pglite'` (`src/core/types.ts:2343`), and the `switch` in `src/core/engine-construct.ts:9-22` (the `default` throws).
2. Add an engine list to the test. Two existing helpers show the pattern. `test/helpers/two-engine.ts` has `type EngineKind = 'pglite' | 'postgres'` and `openTestBrain(kind, settings)` through `createEngine({engine: kind})`. `test/helpers/test-backends.ts` has `TestBackend = 'pglite' | 'postgres'`, `testBackends()`, and env `GBRAIN_TEST_BACKEND` (values `postgres`, `postgres-direct`, `pgbouncer`; anything else throws). The parity file reads neither. Its matrix runs (`scripts/e2e-backend-matrix.txt:33`, `scripts/e2e-matrix.ts:36`) only rerun the same file.
3. Replace `pgEngine` / `pgliteEngine` pairs with `arms` (as in 2714-2729), or add a third variable to each of the 16 `beforeAll` blocks.
4. Gate the Rust arm on its own env var, and make the PGLite arm run without `DATABASE_URL`. Otherwise the Rust comparison can only run where Postgres exists. `.github/workflows/e2e.yml:423` runs the file as `tier1 engine-parity`.
5. Replace or skip the EXPLAIN-based block (1557-1605) and the `jsonb_typeof` probes (1744-1752) for Rust. They inspect Postgres catalogs.
6. Replace the `executeRaw` seeding with typed calls, or provide a Postgres-SQL subset executor (see section 4, SQL surface).

### Parity risks noted

- **Harness is Postgres-bound.** `test/e2e/helpers.ts` (`setupDB`, `setupLegacyEmbeddingDB`, `teardownDB`) uses `src/core/db.ts` and `PostgresEngine` directly, and TRUNCATEs tables. A Rust engine needs its own setup helper; there is no engine-level switch to reuse.
- **Gating hides PGLite.** Everything except the `getRawData` block is inside `describeBoth`. Without `DATABASE_URL`, the file runs 1 test. The header comment (lines 12-14) and `docs/TESTING.md:509` ("each E2E file keeps a PGLite arm in the unit lane") both say otherwise. A Rust arm will be hidden the same way unless the gating changes.
- **Raw SQL surface.** 46 `executeRaw` sites plus `installFixtureChunks` rely on Postgres SQL (`now()`, `interval`, `generate_series`, `ON CONFLICT`, `::jsonb`, `::timestamptz`, `ANALYZE`) and on the projection tables (`page_projection_jobs`, `text_projection_revision`, `knowledge_revision`, `search_vector`). An embedded Rust engine that does not run this SQL cannot pass without test rewrites.
- **Postgres-only introspection.** `test/helpers/timeline-plan.ts` runs `EXPLAIN (FORMAT JSON)` and asserts `Index Name` / `Index Cond` (1592-1604). Replace it with a Rust query-plan assertion or drop it for Rust.

- **Null vs undefined.** `toBeUndefined` (505-507, 541-543) vs `toBeNull` (433-435) on different fields. A generic "null for missing" serializer fails one set of tests.

- **Fixture protocol coupling.** `installFixtureChunks` (17 uses) depends on the projection revision protocol in `src/core/page-state/projections.ts`. Any Rust storage model must implement that protocol, or the fixture must be rewritten to call a public seal API.
- **Unsealed chunk visibility.** `upsertChunks` writes are invisible to default `getChunks` until sealed (942-945). A Rust engine that exposes chunks immediately fails 942.

### Native module precedent: `native/locks/`

**Contents.** `native/locks/locks.c` is a C Node-API v3 addon (`NAPI_MODULE_INIT` at line 301, `napi_define_properties` at line 333) exposing `openLock`, `tryLock`, `close`, plus Windows IPC, plus export publication (`export-publication.h`). POSIX uses `flock`; Windows uses `LockFileEx`.

- `native/locks/README.md`: design and CI notes. Says all eight addons are checked in so source installs work with `bun install --frozen-lockfile --ignore-scripts`.
- `native/locks/manifest.json`: `version 1`, `napi 3`, `zig 0.14.1`, `input_sha256`, and per-artifact `sha256` and `bytes` for eight targets (`linux-x64-glibc`, `linux-arm64-glibc`, `linux-x64-musl`, `linux-arm64-musl`, `darwin-x64`, `darwin-arm64`, `win32-x64`, `win32-arm64`).
- `native/locks/package.json`: private package boundary, not a package. Its README note says this prevents plugin hosts from treating the whole checkout as one native package (#6026).
- `native/locks/prebuilds/*.node`: exactly the eight binaries, checked into git.
- `native/locks/vendor/node-v22.15.0/`: `node_api.h`, `node_api_types.h`, `js_native_api.h`, `js_native_api_types.h`, `LICENSE`, vendored from Node v22.15.0.
- `native/locks/abi-check.c`: compile-time layout checks (`_Static_assert` for Darwin `stat`, open flags, lock constants). Compiled only on macOS against the real SDK in `native-locks.yml`.
- `native/locks/darwin-abi.h`, `windows-napi.h` (resolves used Node-API symbols from the running executable, so it does not load a separate `node.exe`), `windows-ipc.h`, `export-publication.h`.

**Build.** `scripts/native/build.ts` compiles with pinned Zig 0.14.1 via `zig cc -target <triple> -shared -fPIC -O2 -s -DNAPI_VERSION=3`. Targets are glibc 2.17 baseline, musl, `x86_64-macos.13.0`, and `x86_64-windows-gnu`. It sets `SOURCE_DATE_EPOCH` and `-Wl,--build-id=none` for reproducible bytes (`build.ts:39-50`). `scripts/native/toolchain.json` pins archive URLs and SHA-256 (zig for x86_64/aarch64 linux, macOS, Windows). `scripts/native/verify.ts` recomputes `input_sha256` and compares artifact bytes against a rebuild; `--write-manifest` regenerates the manifest. The README says the rebuild must be byte-identical across CI runners.

**Load from Bun.** `src/core/persistence/native-lock.ts`:

- `loadBindingSync()` (lines 94-140) picks a literal `require('../../../native/locks/prebuilds/<target>.node')` by `process.platform`/`process.arch`/detect-libc (`familySync`, `GLIBC`, `MUSL`). Literal requires are deliberate: "Bun embeds each .node asset in its compiled executables. Dynamic prebuild discovery does not embed them." (comment at lines 105-107).
- It validates `binding.target === target` and that required functions exist, then caches. Errors become `NativeLockUnavailableError` with code `writer_lock_unavailable` (lines 27-33).
- Lazy: loaded only by callers that need a lock. `nativeLockCapability()` and `nativeExportPublisher()` expose capability checks.
- No `process.dlopen`, no `createRequire` for `.node`, no loader module beyond this one file. `src/core/cli-socket/peer-cred.ts:20`, `:38` and `src/core/pid1-reaper.ts:91-94` use `bun:ffi` `dlopen` against system libs (`libSystem.B.dylib`, libc), not gbrain-owned addons.

### Binding options

Current Bun facts used below (sources at the end):

- Bun supports Node-API and `require()` / `process.dlopen()` of `.node` files. Compatibility is "best effort" for the exact addon, Bun version, OS and arch. Bun 1.4 aligned N-API status and error behavior with Node 26 and added `napi_create_async_work` and threadsafe functions with teardown fixes.
- napi-rs treats Bun as best effort; its Bun test job is non-blocking upstream, so each addon must be tested on Bun before support is claimed.
- `bun:ffi` is still experimental; Bun's docs say not to rely on it in production. `dlopen`, `JSCallback` are engine-native in current Bun. `threadsafe: true` callbacks marshal to the JS thread with a per-call cost.
- `node:wasi` in Bun is partial: `wasiImport` and `start()` work, `getImportObject()` and `sock_accept` are missing, and WASI preview1 has no `mmap`.

#### Option 1: napi-rs native addon (in-process)

| Aspect | Assessment |
|---|---|
| Bun fit | Good for the `.node` precedent already in the repo. Bun 1.4.4 is the repo floor (`package.json:261-262`, `>=1.4.4`). Bun 1.4 covers async work and threadsafe functions. napi-rs says Bun is best effort, so the repo must own a Bun test lane. |
| Async and threads | `napi_create_async_work` and threadsafe functions are supported. Use them for blocking Rust I/O so the JS thread is not blocked. Teardown rules still apply: join native threads before the environment is torn down. |
| Buffers and embeddings | Input `Buffer`/`TypedArray` can be read in place with `napi_get_buffer_info` (already used in `export-publication.h:509`). Copy-in is safe. Zero-copy out to JS (external ArrayBuffer with a finalizer) is a napi feature whose behavior under Bun must be verified before depending on it; not verified here. |
| Prebuild matrix | Same 8 targets as `native/locks`. napi-rs cross-build: musl via `cargo-zigbuild` (adds `-crt-static` off); Windows MSVC via `cargo-xwin` (GNU Windows not supported in that mode). The repo's zig-cc pipeline does not build Rust. Use `napi build -x` or native CI runners per target, and keep the byte-compare or rebuild-verify step if the repo wants the `verify.ts` guarantee. Windows arm64 and musl are the least-tested on Bun per the napi-rs note. |
| `bun build --compile` | Works if the `.node` is reached by a literal `require`, as `native-lock.ts:108-122` does. Bun may extract the addon to a temp file at runtime; `TMPDIR` must be absolute (Bun issue 45054). Verify with the existing `release.yml:175` style assertion. |
| Crash isolation | None. A segfault, abort or uncaught Rust panic kills the gbrain process (CLI, `serve`, cron). Every exported function needs `catch_unwind`. |
| Multi-process | Each gbrain process would open the store in-process, so the store needs a single-writer story. The repo already has `native/locks` `flock` and the owner-socket routing used for PGLite; both can be reused. Two addons would load in one process (lock addon plus engine addon). |
| Per-call overhead | Lowest of the four: a napi call and marshalling, no syscalls or serialization. |
| Startup | One `dlopen` per process. No extra process. |
| Effort | Medium: Rust crate, napi bindings for the `BrainEngine` surface (or a narrow C-ABI-like surface wrapped in TS), prebuild matrix, Bun CI lane, compile smoke. |
| Risk | Medium-high. Crash blast radius; Bun napi gaps for newer APIs; prebuild matrix cost (8 binaries, reproducibility vs cargo output). |
| Parity tests | Run `test/e2e/engine-parity.test.ts` with the third engine factory, same as PGLite and Postgres; add a `native-lock-prebuilds`-style test (binary target check, manifest hashes) and a compiled-binary smoke (`scripts/native/compiled-smoke.ts` pattern). |

#### Option 2: Rust sidecar process (stdio or unix socket, JSON-RPC or binary framing)

| Aspect | Assessment |
|---|---|
| Bun fit | Pure TS client; no Node-API. Bun `child_process` / `Bun.spawn` plus a unix socket. Matches the repo's existing owner-socket and `cli-socket` design (`src/core/cli-socket/server.ts` header: "The serve side of the warm CLI socket"; `src/core/persistence/local-client.ts`). |
| Crash isolation | Full. A Rust crash kills the sidecar, not gbrain; the TS side can restart and reconnect (the repo already has reconnect machinery for Postgres in `degraded-engine.ts`). |
| Multi-process | Natural single writer: the sidecar owns the store and serializes CLI, MCP and cron requests. This is the main architectural advantage given the repo's current PGLite single-writer lock and owner-socket routing. Requires the sidecar's own lifecycle (start, lock, shutdown, stale socket cleanup, peer-uid checks as in `cli-socket/peer-cred.ts`). |
| Per-call overhead | Highest. A syscall or socket round trip plus framing per call. JSON is expensive for embeddings (`f32` vectors); use length-prefixed binary frames for vectors and bulk page bodies. Not measured. |
| Startup | Per-CLI-invocation cost: spawn the sidecar and open the store, unless the sidecar stays resident (the owner socket pattern). The repo already tunes one-shot reads (`engine-connect.ts:34-42`), so this matters. Measure before committing. |
| `bun build --compile` | The sidecar binary must be embedded as a file asset (`import ... with { type: 'file' }`, the `pglite-embedded-assets.ts` pattern), extracted or read from `/$bunfs`, and run with the executable bit preserved. The exec-bit and extraction behavior in compiled binaries is not verified here. |
| Prebuild matrix | Standard Rust cross-compile per target (no Node-API ABI matrix); the output is one executable per platform rather than a `.node`. Windows and musl still need runners. |
| Effort | Medium-large: protocol design, supervisor, lifecycle, error mapping into `opError` shapes, reconnect, embed-and-extract for compiled binaries, plus the same CI matrix. |
| Risk | Medium. Latency and marshalling; two processes to keep in sync on version; a second lock domain; sidecar orphaning on crash. |
| Parity tests | Same engine-parity suite via the TS client. Add process-kill and restart tests (the persistence-chaos suites are the model), stale-socket cleanup, and a concurrency test for CLI + MCP + cron against one sidecar. |

#### Option 3: WASM (wasm32-wasi / wasm-bindgen)

| Aspect | Assessment |
|---|---|
| Bun fit | Mirrors PGLite's model: WASM loaded in-process, assets embedded via `with { type: 'file' }` (`pglite-embedded-assets.ts`). No native packaging per platform: one artifact runs everywhere. |
| Filesystem | WASI preview1 `preopens` work in Bun but are partial and not a security sandbox (Node and Bun docs both say so). No `mmap`: a storage engine must use linear memory and ordinary file I/O, which constrains page-cache and index design. |
| Locks | WASI has no `flock`. The single-writer lock in `native/locks` is a native addon. A WASM engine would need a host import (napi or ffi) for locking or accept single-process use. This is a real gap for the CLI + MCP + cron model. |
| Threads | WASM shared memory and atomics work with workers; WASI itself has no thread creation. Bun supports the shared-memory path, but this is more complex than a native build. |
| Performance | Unknown for this workload; usually slower than native for vector and index work, and no native SIMD guarantees. Not measured. |
| Crash isolation | In-process trap, so a Rust panic is a WASM trap that can still kill the gbrain process unless caught at the boundary. |
| Effort | Large for a storage engine: WASI file semantics, locking, memory limits (wasm32 is 4 GB addressable), and performance work. |
| Risk | High for a storage engine; low risk for pure compute such as a chunker or ranker. |
| Parity tests | Same engine-parity suite; plus WASI file-semantics tests (fsync, rename, lock failure) and a memory-growth test. |

#### Option 4: `bun:ffi` with a C ABI

| Aspect | Assessment |
|---|---|
| Bun fit | Bun-only, experimental per Bun's docs. gbrain already uses `bun:ffi` for small syscalls (`src/core/cli-socket/peer-cred.ts:20-40`, `src/core/pid1-reaper.ts:89-94`), so the team has the pattern. |
| Surface | Rust `cdylib` with a C header (cbindgen) and `dlopen(path, { symbols })`. Scalar and pointer calls are straightforward; a storage API with owned buffers and handles needs manual free functions. |
| Callbacks | `JSCallback` is not thread-safe by default; `threadsafe: true` adds a per-call marshalling cost. Avoid callbacks from Rust threads in the design. |
| Async | No Node-API async-work equivalent; async must be built with Rust threads and polling or a `threadsafe` callback. |
| `bun build --compile` | Same embedding question as napi: the `.dlopen` path must be a file that exists at runtime; extraction needed. Not verified for ffi specifically. |
| Crash isolation | None (same as napi). |
| Effort | Medium for scalars, large for a full `BrainEngine`. |
| Risk | High: experimental API; Bun may change it; no Node-API stability. |
| Parity tests | Same as napi; add ABI and free-function leak tests. |

### Recommendation (open question for the repo owner)

Open question: does the first Rust engine need crash isolation and a single writer across CLI, MCP and cron, or is in-process speed the priority?

- If speed and simplicity matter most: napi-rs in-process. It reuses the proven `.node` load and compile-embed path in `native-lock.ts`, has the lowest per-call cost, and fits the Bun-only floor. Cost: a Rust panic or segfault takes the whole gbrain process, so every export must catch panics, and the store needs a single-writer answer (reuse `native/locks` flock and the owner socket).
- If crash isolation and one writer matter most: sidecar. It maps onto the existing owner-socket design, but it adds per-call marshalling and startup cost that must be measured against the one-shot read paths in `engine-connect.ts`.
- WASM is a poor fit for a storage engine given no mmap and no flock in WASI. bun:ffi is experimental and better kept for small syscalls.

My suggestion, not decided: start with napi-rs in-process, keep the engine surface behind `constructEngine`, and keep a sidecar as the fallback if crash isolation becomes a requirement. Both need the same engine-parity suite, and both need a Bun CI lane because napi-rs does not block on Bun.

### Parity risks noted

- The kind discriminator is a closed union in at least five places (`engine.ts:832`, `types.ts:2343`, `config.ts:37`, `embedded-engine.ts:14`, `degraded-engine.ts:63`, plus `engine-status.ts:108`). Missing one will type-check or silently fall through.
- About 29 kind branches sit in `schema-migrations/`, and `sqlFor` only knows `postgres|pglite`. A non-SQL engine must not silently get the Postgres or PGLite SQL.
- `migrate.ts:221` treats `pglite` as the transactional-migration special case; a third engine's transaction semantics must match.
- PGLite single-writer lock and owner-socket routing are the only multi-process coordination; a third engine needs an equivalent or CLI+MCP+cron can double-write.
- `degraded-engine.ts` is Postgres-only; a third engine has no degraded-serve story unless added.
- `engine-open.ts` `checkSettings` refuses unknown engines, and `openEngine` is the embedding surface; a third engine must be added there or embedders cannot open it.
- The `--pglite` init flag and `init.ts:170-181` "preserve existing postgres engine" logic need a parallel rule for the new engine, or `init` can flip an existing brain.
- `docs/ENGINES.md:1566-1596` "Adding a new engine" step 4 implies a free-form engine string that the types reject; the doc is out of date with the code.
- Compiled binaries: addon and sidecar embedding is verified in source (`native-lock.ts:105-107`, `release.yml:175`) but not for a napi-rs addon or a file-asset sidecar on this repo's targets.
- Release binaries build only `linux-x64` and `darwin-arm64` (`release.yml:121-131`), while the lock addons cover 8 targets; a Rust engine would need an explicit target policy.
- napi-rs Bun support is best effort upstream; without a repo-owned Bun CI lane on each target, a Bun regression can ship unseen.
