# Explicit-consent embedding migration

`gbrain migrate embeddings` moves the primary text embedding space to a
supported model on both PGLite and Postgres. It coordinates schema, config,
invalidation and a resumable re-embed. Changing a provider identifier or
dimension in config alone does not convert stored vectors.

The original v0.46.3 notice concerned a hosted provider that retired on
2026-09-04. That integration, its switch command and its provider-ID
self-hosting workaround have been removed. This file retains the generic
migration workflow, not the obsolete provider-specific playbook. Original
instructions are preserved at Git revision
`6040075c6cb95be5881cc2e1b76ef7d71f4e5d29` (retained on 2026-09-23).

**No upgrade, warning or old pending action item authorizes this work.**
Migration can delete incompatible vectors and incur a full re-embedding bill.
Keep a verified full backup and obtain explicit approval for the selected
brain, target model, dimensions, reranker action and cost before proceeding.

## 1. Inspect the intended brain without spending

Resolve the brain first using [brain routing](../conventions/brain-routing.md).
This operation affects all sources in that brain, not just the current source.
Only the brain's owner should perform it; a mounted consumer asks the owner.

```bash
gbrain migrate embeddings --status
```

Inspect the actual column widths, NULL-vector counts, page-signature census,
config planes and any in-flight marker. Do not infer completion from the
environment or a configured model name. No stored provenance should be
rewritten to make an old vector appear to belong to a new model.

`GBRAIN_EMBEDDING_MODEL` and `GBRAIN_EMBEDDING_DIMENSIONS` override file config
for every process. Conflicting values make a live migration refuse. Review
the env in workers, cron and shells; coordinate any changes with the owner.
Do not use `--ignore-env-override` to bypass an unexplained mismatch.

## 2. Choose a supported target and preview

Voyage's new-install default is `voyage:voyage-4` at 1024 dimensions. One
`VOYAGE_API_KEY` covers its embeddings and `voyage:rerank-2.5` reranker.
OpenAI is another supported option; `text-embedding-3-small` can retain an
existing width up to 1536. Retaining the width avoids a schema resize, not
the re-embed required for a different vector space. Local providers require
an explicitly selected model and its real output width.

Configure the chosen key securely in the environment or the provider's
file-plane API-key setting. Never print or copy the key into an action report.

```bash
gbrain migrate embeddings --to voyage:voyage-4 --dim 1024 --dry-run
```

Show the plan to the user: affected brain and sources, old and new widths,
chunk count, estimated spend (or unavailable estimate), reranker action,
pending fact vectors and any content-tier downgrade. **1280 is not a valid
Voyage width**; supported widths are 256/512/1024/2048. A width change rebuilds
the dim-pinned text columns and indexes; image/multimodal columns stay separate.

## 3. Obtain approval, quiesce writers, then run

Confirm the backup and coordinate stopping or draining embedding writers
before the migration. Do not stop services without the owner's approval.
The plan warns about concurrent jobs; migration locks are not permission to
ignore another writer.

Only after approval, replace `--dry-run` with `--yes`:

```bash
gbrain migrate embeddings --to voyage:voyage-4 --dim 1024 --yes
```

Without `--yes`, an interactive caller must confirm; a non-TTY caller exits
2. A spending posture does not waive the migration's destructive-change
consent gate. The live run probes the target before mutation. A failed probe
does not authorize a fallback provider or a different model.

`--reranker auto` is the default companion action. Review it in the plan, or
explicitly choose `--reranker off`, `--reranker keep`, or a supported model
such as `--reranker voyage:rerank-2.5`. A failed reranker probe keeps its prior
config and reports `switch_failed`; it is not successful reranker migration.
OpenAI has no reranker on its key, so do not silently enable a third provider.

## 4. Verify actual state

```bash
gbrain migrate embeddings --status
```

Check target widths, remaining chunk vectors, signature census, in-flight
state and the recorded smoke-check result. A converged config value alone is
not proof. Semantic retrieval is degraded for content not yet re-embedded.
After approval for any provider calls, search for a known page as a separate
behavioral check; distinguish that check from the spend-free status output.

Fact-vector repair is separate and consented. Inspect the pending census;
follow [fact-vector repair](../../docs/embedding-migrations.md) rather than
claiming every fact was backfilled by the primary migration.

## Recovery and boundaries

- Re-run the same approved target after a kill or partial failure. Status
  prints the exact resume command; chunks already in that space are retained.
- A different in-flight target refuses. Use `--retarget` only after explicit
  approval to abandon that target and review the new cost.
- A lost or held lock means paused, not complete. Inspect the reported lock
  and jobs before retrying; do not clear another writer's lock.
- `--no-embed` stages schema/config/invalidation but does not complete a
  migration. Finish the approved re-embed with
  `gbrain embed --stale --catch-up --include-null-signature`.
- Custom `embedding_columns` have no automatic migration here. Changing
  their model labels does not convert their vectors. Plan a separate,
  explicitly approved replacement or removal with the owner.
- A keyless brain with embeddings disabled does not need paid migration
  merely because it was upgraded. Preserve that opt-out.

See the [full migration reference](../../docs/guides/embedding-migration.md)
for the transaction, resume and config-plane contracts.
