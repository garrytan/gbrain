A write refused during publication by a persistence protocol guard (SQLSTATE 42501) now fails with the guard's own code on its receipt, `writer_upgrade_required`, `writer_not_quiesced`, `unsupported_mutation_protocol` or `writer_coordinator_required` (relationship `unreadable_state` when the database role cannot read the writer state), with `write_error_detail` naming the guard and a suggestion for that refusal, instead of `storage_error` for an unexpected owner exception. `gbrain sources writer status` gives the same step in `recent_failures[].next_action`. Any other permission error is unchanged, and so is the same refusal outside publication (write admission, protocol activation), which still reports `permission_denied`. Every `unreadable_state` refusal (#7780) now reads "writer state this database role cannot fully read (row-level security hides it or applies to the role, or a singleton row is missing)", its receipt suggests running gbrain as a role that can read that state instead of upgrading, and `gbrain sources writer status` shows the table in `recent_failures[].error_detail.state`.
