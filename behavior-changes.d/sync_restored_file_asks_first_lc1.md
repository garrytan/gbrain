A file you restore after gbrain delete removed it (git checkout, a revert, or a commit that re-adds it) now goes through the file-drift consent step instead of being ignored. The next managed sync holds the file (file_drift, side deleted, state tombstone_edited, or purged_differs after the retention purge) and the page stays deleted. gbrain sources status and doctor list the hold, and gbrain repair file-drift --held --side deleted --state <state> --prefer file previews bringing the page back and does it only after you agree; --prefer database keeps the deletion and removes the file. The first managed sync after the upgrade reads the checkout once more, so it finds such a file even when nothing else changed. Before, sync settled the restored file as already up to date, and after the 72-hour purge the page was gone for good. A deletion that stands is unchanged: a delete that left the file (sync.write_through off, a read-only mirror), a delete whose removal is not committed yet, a --purge delete, and a git-canonical source settle with no hold.
